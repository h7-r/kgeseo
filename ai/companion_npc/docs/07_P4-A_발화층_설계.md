# P4-A — NPC 발화층 (안전한 발화 기반)

> 작성 2026-10-26 · 상태 **P4-A 구현 · P4-B 계획** · 코드 `src/companion_npc/speech/` · `contracts/npc_content.py` · `adapters/npc_merge.py` · 테스트 `tests/test_speech.py`
>
> 네트워크와 LLM 을 쓰지 않는다(GPT · Qwen 은 P4-B). 평가 지표는 구조 지표다. 발화 품질 평가가 아니다. 테스트 견본의 힌트·지식은 실제 승인 콘텐츠가 아니다.

## 1. 구조

```
.client.json ─┐
.server.json ─┼→ P2-A 변환기 (draft 팩) ─┐
              │                          ├→ npc_merge (판 고정 확인 · 누설 검사 · 상태는 승인 상태 그대로) → 결합 팩
.npc.json ────┴──────────────────────────┘
                                                  │
NpcContext + SpeechPlan(kind · initiator · 대상) ──┴→ 사전 조건 → 검색(거른 뒤 TF-IDF) → PromptPayload
   → 생성기(Template · Fake · 향후 GPT · Qwen) → 공통 안전 검증 → NpcUtterance
                                        └ 실패 → 승인 템플릿(재검증) → 그래도 실패 → 보류
```

판단 모델 없이도 돈다. 발화 계획은 바깥(테스트 · 플레이어 요청 · 판단층)이 준다.

## 3. `.npc.json` v0.1 초안

> 팀 저장소에 공식 계약이 없어 **테스트 fixture 기준으로 설계한 초안**이다. backend 의 공식 게시 계약으로 확정한 것이 아니다. 최종 게시 권한은 서버와 팀 콘텐츠 승인 절차에 있다.

| 필드 | 내용 |
|---|---|
| `content_id` · `content_version` | NPC 콘텐츠 판 |
| `case_id` · `case_content` | 승인할 때의 사건 콘텐츠 판 (client · server 정규화 해시). 다르면 결합하지 않는다 |
| `publication` | `status`(draft · approved · published · withdrawn) · 승인자 · 승인 시각 · `history`(시간순, 마지막 기록 = 현재 상태, 승인 기록 필수) |
| `premise` · `persona` | 브리핑 · 페르소나 (approved·published 면 premise 필수) |
| `hints` | 승인 NPC 힌트 1·2단계 (`ApprovedHint`) |
| `knowledge` | 지식 조각 — 스포일러 등급 · 공개 조건 (`KnowledgeChunk`) |
| `templates` | `check_in` · `clarify_general` · `clarify_with_object`(`{object}` 만 허용) |

- **넣지 않는 것**: 정답 · 정답 별칭 · 판정 규칙 · 조합 짝. 모든 모델이 `extra="forbid"` 라서 넣으면 거부된다.
- **견본의 상태**: `tests/fixtures/npc/*.npc.json` 의 approved · published 와 승인 기록(`test-fixture`)은 테스트용 상태다. 실제 팀 승인이 아니다.
- **별칭의 위치**: 정답 별칭은 서버 비공개 정보다. 테스트에서는 `tests/fixtures/private/aliases.json` 이 그 자리를 대신한다. 운영에서는 서버 비공개 저장소에 둔다.

### 결합 규칙 (`npc_merge`)

1. 사건이 같고, 팩이 draft 이고, **판 고정 해시가 같아야** 결합한다.
2. NPC 콘텐츠의 모든 문장(페르소나 · 브리핑 · 힌트 · 지식 · 템플릿)을 정답 · 별칭과 대조한다. 걸리면 팩을 만들지 않고, 오류에는 위치만 적는다.
3. 팩의 공개 상태는 NPC 콘텐츠의 승인 상태를 따른다. **결합이 상태를 올리지 않는다.**
4. 공개 상태면 누설 검사 통과 기록을 남긴다(시각 = 승인 시각, 재현성).
5. 서버 비공개 정보는 팩에 들어가지 않는다(테스트로 확인).

## 4. 발화 범위와 사전 조건

| 유형 | 시작 | 사전 조건 | 검색 | 생성(P4-A) |
|---|---|---|---|---|
| `check_in` | 자동 | — | **하지 않음** | 승인 템플릿 |
| `clarify` | 플레이어만 (자동이면 check_in 으로) | — | 현재 구역 · **FE 가 지금 보인다고 확인한** 오브젝트(`confirmed_visible_object_ids`)의 이름 조각(등급 0). 확인이 없으면 비운다 | 기본은 일반 질문. 확인된 이름을 플레이어 메시지가 짚었을 때만(TF-IDF ≥ 0.3) 이름을 넣은 템플릿 |
| `nudge` | 자동 · 플레이어 | 대상 확인 · 미완료 · 승인 1단계 힌트 · 힌트 조각의 공개 조건 열림 · 단계 상한 | 등급 ≤1 · 대상 퍼즐 조각 + 등급 0 배경 | 승인 힌트 본문 |
| `hint` | 자동 · 플레이어 | 같은 조건 + 2단계 | 등급 ≤2 · 같은 규칙 | 승인 힌트 본문 |

- **사전 조건을 못 맞추면**: 플레이어 요청 → `clarify`(일반 질문) · 자동 → **보류**.
- **단계 상한**: `limits.max_npc_hint_level` 이 1 이면 hint → nudge 로 내린다.
- **LLM 허용**: LLM 생성기는 `limits.allow_llm` 이 참일 때만 쓴다. 아니면 템플릿으로 바꾼다.
- **Hint API 와의 관계**: 기존 정적 Hint API 의 권한과 단계는 바꾸지 않는다.

## 5. 검색과 정보 접근

1. **거르기 먼저** (`retrieval.allowed_chunks`)
   - 공개 상태 · 사건 일치 (`visible_chunks`)
   - 현재 구역 · 획득 단서 · 완료 퍼즐 · flag 공개 조건
   - 유형 · 단계별 범위 (§4)
2. **그다음 순위**: TF-IDF(글자 2~4-gram). 검색 결과가 비어도 정상 처리한다.
3. **생성기 입력은 더 좁다** (`PromptPayload.to_model_input`)
   - 넣는 것: 유형 · 페르소나 말투 · 승인 힌트 본문 · 허용 조각 본문 · 정제한 플레이어 메시지
   - 넣지 않는 것: 퍼즐·오브젝트·단서 ID, flag 이름, 정답, 공개 조건, case_id
   - 조각은 K1 · H1 같은 임시 라벨로만 부르고, 실제 ID 와의 연결은 서버에만 남긴다.
   - 플레이어 메시지는 제어 문자 · 방향 문자를 지우고 200자로 자른다. 지시가 아니라 데이터로 다룬다.

## 6. 공통 출력 안전 검증 (`guard.SpeechGuard`)

**검사 범위**: 실제 발화 문장만 본다. 구조화된 메타데이터(ID 필드 · 지표 · 해시)는 이 검사의 대상이 아니다. 그래서 숫자 정답이 지표값 안에서 우연히 잡히는 오탐(docs/06 §9.4)을 피한다. 발화 문장 안의 숫자는 그대로 검사한다.

| 검사 | 내용 |
|---|---|
| `answer_leak` | 정답 · 별칭 · 숫자 정답의 한글 읽기(예: 1234 → 일이삼사) |
| `internal_id` | 팩 ID 전체(정규화) · 퍼즐·단서·flag ID 의 연속 두 조각(공개 이름에 있는 조각 쌍은 제외) |
| `undisclosed_content` | 지금 꺼낼 수 없는 조각(윗등급 · 닫힌 공개 조건 · 반전)의 문구가 8자 이상 겹침 (허용 조각·템플릿과 같은 문구는 제외) |
| `kind:*` | check_in 에 사건 이름·지식 문구 / clarify 에 허용 안 된 이름 |
| `ungrounded` | nudge · hint **전체**가 승인 힌트·허용 조각과 4-gram 50% 이상 겹치지 않음 |
| `unsupported_sentence` | nudge · hint 의 **문장·절마다**(문장 끝 · 줄바꿈 · `;` · 그리고/그런데/하지만/그다음 등 접속어로 나눔) 근거 4-gram 이 덮지 못한 연속 글자가 **9자 이상** |
| `too_long` | 280자 초과 |

**실패하면**: 승인 템플릿으로 대체하고 **그 템플릿도 검증한다.** 그래도 실패하면 보류한다(`fallback_failed`).

**문장·절 단위 근거 검사 (P4-A 보완)**
- 전체 일치율이 높아도, 근거 없는 절이 하나라도 있으면 실패한다. 승인 힌트 뒤에 새 사실 · 사건 주장 · 해결 지시를 덧붙이는 우회를 막는다.
- 안전 예외: 정해 둔 짧은 인사·격려(`SAFE_PHRASES`: 좋아요 · 천천히 해 보세요 등)는 덮인 것으로 본다.
- 쉼표로는 절을 나누지 않는다. 짧은 조각이 생겨 정당한 바꿔 말하기를 막았기 때문이다.
- **임계값 9 의 근거와 한계**: 테스트 견본에서 덮이지 않은 최장 구간을 재 보니, 표현이 가까운 정당한 바꿔 말하기는 2~10자, 덧붙인 공격 문장은 9~27자였다. 두 분포가 겹쳐(10 대 9) 깨끗한 경계가 없어서 **안전 쪽을 골랐다.** 견본이 작아(바꿔 말하기 10 · 공격 8) 일반화된 값이 아니다.

**한계**:
- 글자 비교다. 돌려 말하기 · 번역 · 자모 분해 · 철자 읽기는 별칭이 없으면 못 잡는다.
- **승인 힌트 문장 뒤에 정답을 돌려 말해 덧붙이면 통과한다**(평가 `gen_paraphrase_after_hint`, 두 사건 모두 막지 못함).
- 의미 수준 검사와 사람 레드팀은 P4-B 다.

## 9. 발견한 한계

1. **의미 수준 누설을 완전히 막지 못한다.** 덧붙인 문장은 문장·절 검사로 막지만(8/8), 근거 문장 **안에** 짧게 끼워 넣은 표현(6자, 예: "바로 그 둥근 것")은 통과한다(2/2). **문장 단위 검증만으로 의미적 스포일러를 완전히 막는다고 주장하지 않는다.**
2. **clarify 의 이름 매칭은 글자 기반이다.** 오브젝트 이름이 영어(테스트 견본)이고 플레이어가 한국어로 부르면 일반 질문으로 떨어진다. 이름의 한국어 표기·별칭이 NPC 콘텐츠에 필요하다.
3. **오브젝트 가시성은 확정할 수 없다.** 그래서 FE 가 확인해 준 오브젝트(`confirmed_visible_object_ids`)가 없으면 clarify 는 늘 일반 질문이다. 그 확인 신호는 아직 계약이 없다(합의 #35).
4. **템플릿 생성기는 승인 힌트를 그대로 읽는다.** 말투·맥락 적응은 LLM 실험(P4-B)의 몫이다.
5. **근거 검사는 템플릿에 유리하고 정당한 바꿔 말하기를 많이 막는다**(오탐 7/10). P4-B 에서 LLM 발화를 실제로 만들어 오탐률을 다시 재고, 의미 유사도 검사와 사람 평가를 함께 본다. 임계값은 바깥 평가 결과를 보고 고치지 않는다.
6. **파일 작성 중 소스에 보이지 않는 문자(폭 없는 문자·방향 제어 문자)가 들어간 일이 있었다.** 코드 포인트 표기로 고쳤고, 소스·테스트 전체에 그런 문자가 없는지 검사하는 테스트를 더했다.

## 11. 기존 NPC 동행 프로토타입과의 경계

- 프로토타입(`origin/feat/SJ-npc-follow-prototype`)은 이동 · 행동 상태 · 대화창(`NpcDialogViewProps {line, onClose}`)을 맡는다.
- 발화층은 `NpcUtterance`(`speech.text` · `kind` · `display`)만 돌려준다. 행동 상태를 바꾸지 않는다.
- 자동 개입은 `display: bubble` 이고, 플레이어 요청은 `display: dialog` → 대화창 `line` 이다.
- 연결(별도 NPC 서비스 · 병합 시점)은 담당자와 정한다. 이번에 프로토타입·backend 를 바꾸지 않았다.
