# P2-C — 합성 플레이어 시뮬레이터

> 작성 2026-10-25 · 상태 **초안** · 코드 `src/companion_npc/simulation/` · 설정 `experiments/p2c_default.json` · 테스트 `tests/test_simulation.py`
>
> **합성 데이터는 학습 파이프라인의 기능 검증용이다. 실제 플레이어 행동 분포를 대표하지 않는다.**
> 유형별 매개변수는 관찰 근거가 없는 초기 가정값이다. 아래 숫자는 이 가정에서 나온 **합성 데이터의 성질**이며, 실제 플레이어나 모델 성능에 대한 주장이 아니다.

## 1. 구조

```
experiments/p2c_default.json ─┐
P2-A 변환기 → ScenarioPack ────┴→ engine (세션마다 난수 흐름 하나)
     ├─ interaction_events.jsonl            → replay_session → extract_features → label_replay  (P2-B 그대로)
     ├─ session_truth.jsonl                 ┐
     ├─ latent_segments.jsonl               ┘ 합성 정답 — 특성이 다 계산된 뒤 라벨·필터에만 사용
     ├─ synthetic_exploration_events.jsonl  운영 이벤트가 아님 (inspect·navigate)
     └─ manifest.json                       representative: false · seed · 설정/파일 해시
```

| 파일 | 역할 |
|---|---|
| `simulation/config.py` | 설정 모델 + 초기 가정값(`DEFAULT_ARCHETYPES`). JSON 과 같은 값인지 테스트가 검사 |
| `simulation/scenario.py` | 답으로 풀 수 있는 퍼즐 · 도달 가능 · 도달 불가 구분 |
| `simulation/runtime_effect.py` | backend `apply_runtime_effect` 를 같은 순서로 옮긴 것 |
| `simulation/engine.py` | 세션 합성 (잠재 상태 · 이벤트 · 결과) |
| `simulation/analysis.py` | P2-B 파이프라인 통과 · 잠재 상태 붙이기 · 정상 학습 행 · 요약 |
| `simulation/writer.py` · `__main__.py` | 생성 · 파일 쓰기 · CLI |

```powershell
$env:PYTHONPATH = "src"
.\.venv\Scripts\python.exe -m companion_npc.simulation --config experiments\p2c_default.json --out-dir data\synthetic\p2c_default --analyze
```

`data/` 는 깃에서 빠진다. 3,000세션 생성·분석에 약 16초 걸린다.

## 2. 플레이어 유형 (초기 가정값 — 관찰 근거 없음)

| 유형 | 생각 시간 | 탐색 | 정답 확률 | 같은 오답 재입력 | 막힘 | 이탈 |
|---|---|---|---|---|---|---|
| fast_solver 빠른 해결형 | 중앙값 25초 | 0.1 · 60초 | 0.7, 오답마다 +0.1 (최대 0.95) | 0.1 | 없음 | 0 |
| trial_and_error 시행착오형 | 20초 | 0.15 · 60초 | 0.15, +0.1 (최대 0.8) | 0.15 | 6연속 오답 뒤 0.3 · 120초 | 오답당 0.02 |
| repeat_wrong 반복 오답형 | 30초 | 0.1 · 60초 | 깨달음 전 0.05, 오답마다 깨달음 확률 0.08, 깨달은 뒤 0.6 | **0.7** | 3연속 오답 뒤 0.4 · 150초 | 0.05 |
| long_explorer 장시간 탐색형 | 20초 | **0.9 · 180초** | 0.5, +0.1 (최대 0.9) | 0.05 | 8연속 오답 뒤 0.1 | 0.01 |
| dropout 중도 이탈형 | 20초 | 0.15 · 60초 | 시행착오형과 같음 | 0.15 | 2연속 오답 뒤 0.5 · 90초 | **0.25** (막힘 뒤 이탈) |

공통 설정은 다음과 같다.
- away(일시정지·자리 비움): 간격마다 0.1, 중앙값 240초
- 이미 푼 퍼즐 재입력: 5%
- 단서 2개 이상일 때 조합 시도: 10% (늘 실패)
- 내보내기 시각: 시작 + 10~45분
- 최대 세션: 60분

## 3. 잠재 상태와 라벨

| 판단 시점의 상태 | 뜻 | `synthetic_needs_help` | 정상 학습 데이터 |
|---|---|---|---|
| working | 생각·입력 중 | 0 | 포함 |
| exploring | 생산적 탐색 (로그에 안 보임) | **0** | 포함 |
| stuck | 할 일을 모름 | **1** | 포함 |
| away | 자리 비움 | None (판단 대상 아님) | 포함 (도움 라벨은 None) |
| post_end | 자연 종료 이후 | None | **제외** (분석용) |

- 대리 라벨이 censored 인 시점도 정상 학습 데이터에서 뺀다.
- 정상 학습 행에는 특성·라벨·묶음 키(`play_session_id`·`case_id`)만 들어간다. 유형과 잠재 상태는 넣지 않는다.
- 판단 시점이 이벤트 시각과 같을 때(post_event)는 그 시각에 **시작하는** 구간의 상태를 쓴다. 즉 이벤트 직후 플레이어가 하는 일이다.

## 4. 퍼즐 진행 규칙

- **정답을 모른다.** 시뮬레이터는 server.json 을 읽지 않는다. 테스트가 소스에 `accepted_answers` 가 없는지 검사한다. 정답 여부는 확률로 정하고, 답 칸에는 `<SYNTH_CORRECT>` · `<SYNTH_WRONG_k>` 만 넣는다. 팩은 P2-A 변환기로 만든다. 변환기는 정답을 누설 검사에만 쓴다.
- **답으로 풀 수 있는 퍼즐**: 보이는 input 오브젝트가 가리키는 퍼즐. 팩 순서대로 진행한다. backend 에 해금 조건이 없어 처음부터 모두 입력할 수 있다고 본다.
- **도달 가능**: 위 퍼즐과, 그 효과로 완료되는 퍼즐.
- **도달 불가**: 조합으로만 완료되는 퍼즐(조합 성공 제외), 숨은 오브젝트에만 걸린 퍼즐.
- **완료 판정**: `reachable_completed`(도달 가능한 것 전부)와 `scenario_completed`(팩의 퍼즐 전부)를 따로 기록한다.

| 사건 | 답으로 풂 | 도달 가능 | 도달 불가 |
|---|---|---|---|
| case_001 | 1 | 1 | — |
| case_fixture_lighthouse | 2 | 3 | PUZZLE_RECONSTRUCT |
| case_fixture_archive (신규) | 5 | 6 | PUZZLE_RECONCILE |

## 6. 발견한 문제

1. **판단 시점의 65% 가 세션이 끝난 뒤다.** 내보내기 시각(10~45분)이 세션 종료보다 늦으면, 재생이 그 사이를 30초마다 tick 으로 채운다. 그 시점의 대리 라벨은 모두 1 이다. 실제 로그에는 종료 기록이 없어(#19) 이를 가릴 수 없다. 그대로 학습하면 "아무도 없는 시간"을 막힘으로 배운다.
2. **대리 라벨은 탐색과 막힘을 잘 구분하지 못한다.** exploring 0.73 대 stuck 0.90 이다. 장시간 탐색형은 exploring 시점 대부분이 1 이다. away 도 0.90 이라 일시정지가 막힘처럼 보인다.
3. **유형·사건마다 방향이 뒤집힌다.** case_001·lighthouse 의 시행착오형은 stuck(0.29·0.38)이 exploring(0.37·0.54)보다 낮다. 막힌 뒤 곧 풀면 120초 안에 진전이 생기기 때문이다. 합성 데이터 안에서도 대리 라벨과 도움 필요가 일정하게 맞지 않는다.
4. **대리 라벨 censored(11,923)는 세션당 약 4개로 거의 일정하다.** 관측 끝 120초 안의 tick(30초 간격) 수와 같은 구조적 값이다. 대부분(9,913)은 이미 종료 후 시점이라, 종료 전 censored 는 2,010 개뿐이다.
5. **tick 이 행 수를 지배한다.** 세션당 판단 시점 약 54개 중 이벤트는 5개 정도다. 이웃한 tick 은 서로 거의 같아 P3 에서 가중치·표본 추출이 필요하다.
6. **무작위 ID 가 숫자 정답과 겹친다.** UUID 안에 archive 가상 사건의 4자리 숫자 정답이 우연히 나왔다. 글자 비교식 누설 검사를 ID 가 섞인 데이터에 그대로 돌리면 오탐이 난다. 테스트는 UUID·시각·해시를 지운 뒤 검사한다.
7. **case_001 은 퍼즐이 1개라** 세션당 이벤트가 1.4~5.3 개뿐이다. 판단층 특성(대상 전환, 진행 비율)이 거의 변하지 않는다.
8. **long_explorer 는 73% 가 관측 종료로 잘린다**(archive). 도달 완료율 25.5% 는 능력이 아니라 내보내기 시각 탓이다. 완료율을 볼 때 결과(outcome)를 함께 봐야 한다.

## 7. 확인된 사실과 운영 로그에 대한 함의

§6 의 관찰에서 나온 규칙이다.

- **종료·일시정지 이벤트가 없으면 운영 로그에서는 "그 시각에 플레이 중이었나"를 확인하기 어렵다.** 합성 데이터에서는 `ended_at`·away 구간(합성 정답)으로 가렸지만, 운영 로그에는 그 정보가 없다. 같은 필터를 운영 로그에 쓸 수 없다.
- **"무진전" 대리 라벨만으로는 탐색과 막힘을 구분하기 어렵다.** 탐색은 로그에 흔적을 남기지 않아, 겉보기에는 막힘과 같은 공백이다.
- **`synthetic_needs_help` 는 시뮬레이터 가정에서 나온 합성 정답이다.** 사람이 붙이는 `needs_help`(HelpAnnotation)와 다르다. 둘을 같은 열·같은 이름으로 섞지 않는다.
- **잠재 상태·유형·종료 시각 등 시뮬레이터 정답은 모델 입력에 넣지 않는다.** 이 값들은 라벨과 평가 필터에만 쓴다. 테스트가 특성 경로와 학습 행에서 이 값들이 빠져 있는지 검사한다.
