## 1. 12월 정적 힌트와 이 실험은 다르다

| | PRD 12월 범위 (USR-108) | 이 실험 (AI 동행 NPC) |
|---|---|---|
| PRD 위치 | ② 플레이어 기능 · Must | USR-055·056 → **EXT-001 (확장 1순위)** |
| 힌트 수단 | 사람이 쓴 2단계 정적 힌트 (힌트 보기 / 정답 보기) | NPC 가 상황을 보고 끼어들어 **방향만** 제시 |
| 실시간 AI | 없음 | 판단층(분류기) + 발화층(템플릿 / GPT+RAG / Qwen) |
| 정답 공개 | 2단계 「정답 보기」에서 공개 | **어떤 단계에서도 공개하지 않는다** |
| 상태 변경 | Hint API 가 `hint_levels` 갱신 (경로 미확정·미구현) | **하지 않는다.** 읽기만 |

- 이 실험은 12월 정적 힌트를 **대체하지 않는다.** 정적 힌트 UI·Hint API 일정과 무관하게 진행한다.
- 실험 결과는 비교 리포트와 붙이는 방식 제안까지다. 본편 연결은 별도 합의 후 진행한다.

## 2. 두 층 구조 [제안]

```
          ┌──────────── NpcContext ────────────┐
          │ state(=PlaySessionState) · 최근 인터랙션 │
          │ 타이밍 · 트리거 · 포커스 · 제한            │
          └───────────────┬────────────────────┘
                          ▼
  판단층  rule │ logreg │ lightgbm   → decision {개입?, npc_hint_level, 대상 퍼즐}
                          ▼
  검색    visible_chunks(ScenarioPack, case_id, state, max_tier)   ← 차단 먼저, 순위는 나중
                          ▼
  발화층  template │ gpt_rag │ qwen_local  → speech
                          ▼
  안전    정답 누설 검사 (서버 쪽, accepted_answers + 별칭)
                          ▼
                     NpcUtterance
```

- **판단층**은 시나리오와 무관한 피처만 본다. 시도 횟수, 마지막 진전 뒤 경과 시간, 같은 오답 반복(answer_fingerprint), 단서 획득 비율, 이전 NPC 개입 단계 등이다. 퍼즐 ID를 피처로 쓰지 않는다.
- **발화층**은 ScenarioPack 과 판단 결과만 본다. 시나리오 지식은 전부 데이터로 들어오므로, 새 사건이 와도 **모델 코드를 고치지 않는다.**
- 네 방법은 하는 일이 달라 같은 축에서 비교할 수 없다. 그래서 층별로 비교한다.

| 층 | 기준선 | 비교 대상 | 주요 지표 (P3~P4 에서 확정) |
|---|---|---|---|
| 판단 | 규칙 | 로지스틱 회귀 · LightGBM | 개입 F1, 개입 시점 오차, **케이스 밖 일반화** (학습에 안 쓴 사건으로 평가) |
| 발화 | 템플릿 | GPT API + RAG · 로컬 Qwen + 같은 RAG | 정답 누설률, 근거 일치율, 말투 적합, 지연, 비용 |

## 3. 스포일러 · 데이터 보호 원칙

1. **`accepted_answers` 는 LLM·클라이언트에 건네지 않는다.** ScenarioPack 에 그 필드가 없고, 모든 계약이 `extra="forbid"` 라서 섞여 들어오면 검증에서 거부된다.
2. **힌트는 사람이 승인한 데이터(`ApprovedHint`)로 관리한다.** 발화가 힌트(수준 ≥ 1)이면 `grounding.hint_ids` 에 승인 힌트가 하나 이상 있어야 한다.
3. **NPC 힌트 수준 2도 정답이 아니다.** `npc_hint_level` 은 backend `hint_levels` 와 다른 축이다(§4).
4. **정답 판정·상태 변경은 backend 책임이다.** NpcUtterance 에는 `state_changes` 가 없다.
5. **RAG 는 검색 단계에서 막는다.** `visible_chunks` 는 다음 순서로 거른다.
   - 공개(`published`) 팩만 쓴다.
   - 플레이 중인 사건의 팩만 쓴다.
   - `spoiler_tier ≤ 판단된 수준` 인 조각만 쓴다.
   - 공개 조건(현재 zone · 획득 단서 · 완료 퍼즐 · flag)을 만족한 조각만 쓴다.
   - 이미 푼 퍼즐의 힌트는 뺀다.
6. **누설 검사는 서버에서 돌린다.** 팩을 만들 때 한 번(`safety_audit`), 발화 직후 한 번(`safety`) 돌린다. 공개 팩은 검사 통과 기록이 있어야 하고, 발화는 검사를 통과해야 내보낸다.
7. **플레이어 답 원문은 받지 않는다.** 같은 오답이 반복되는지는 서버가 만든 해시(`answer_fingerprint`)로만 안다.

## 4. 힌트 수준 — 두 축을 섞지 않는다

| 값 | backend `hint_levels` [확정·호환] (파이프라인 설계요청 v2.1 §4.6) | NPC `npc_hint_level` [제안] |
|---|---|---|
| 0 | 미열람 | 개입 없음 / 잡담 |
| 1 | 다음 사고·행동 안내 (정답 비노출) | 주의 환기 — 어디를 다시 볼지 |
| 2 | **정답 또는 정확한 조작 공개** | **방향 제시** — 다음 생각의 방향 (정답 비노출) |

NPC 는 backend `hint_levels` 를 읽어 피처로 쓸 수 있지만 **바꾸지는 않는다.**
backend 의 2단계(정답 보기) 문구는 정답과 같으므로 ScenarioPack 에 넣지 않는다.

## 5. 기존 기능과의 관계

| 대상 | 관계 |
|---|---|
| `backend/` | **읽기 전용.** 테스트가 `app.schemas` 의 닫힌 값 목록과 `case_001` JSON 을 읽어 일치 여부만 검사한다 (`tests/test_backend_compat.py`). |
| `origin/feat/SJ-npc-follow-prototype` | **읽기 전용 참고, 병합하지 않는다.** `gameEvents.ts` 의 3종 이벤트를 `Trigger.type` 에, `behaviorState.ts` 의 Idle/Follow/Interact 를 `NpcContext.npc_behavior` 에 맞췄다. 나중에 붙일 때는 그 컨트롤러가 NpcUtterance 를 받아 대화창을 여는 형태가 자연스럽다 [미정]. |
| GameSpec / PuzzleSpec | **아직 스키마가 없다.** 확인 결과는 아래와 같다. |
| PRD `Claude outputs/` | `.gitignore` 대상이라 내 컴퓨터에만 있다. 이 문서는 PRD 항목 번호만 인용한다. |

### GameSpec / PuzzleSpec 확인 결과 (2026-10-24, 모든 원격 브랜치 검색)

- **main** 에는 없다.
- **PRD ADM-090** 에 「GameSpec / PuzzleSpec / case_version, 상세 스키마는 별도 Backend/API/Data Spec 문서」라고만 적혀 있다. 그 Spec 문서는 저장소에 없다.
- **`origin/dev`** 의 `docs/퍼즐_제작_다중_에이전트_파이프라인_설계요청_v2.1.md` (2026-10-01) 는 설계 **요청서**다. 산출물 이름(`CompiledPuzzleSpec`, `PuzzleGraph`, `TelemetrySpec` 등), 공통 메타데이터(§9.2), Provenance 형식(§9.3), Puzzle Type 7종(§4.4)만 정의한다. 필드 단위 스키마는 없다.
- 그래서 ScenarioPack 은 **지금 있는 것**(backend case client/server JSON)에서 만들 수 있게 설계했다. 위 요청서의 Provenance·Puzzle Type·artifact_id 형식을 미리 따라, GameSpec 이 확정되면 변환기만 추가하면 되게 했다.
