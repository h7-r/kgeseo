## 2. 대상 퍼즐과 개입 종류

| 대상 관측 | 뜻 | 허용하는 개입 |
|---|---|---|
| `observed_focus` | FE 가 지금 그 퍼즐을 보고 있다고 알려 왔다 | **퍼즐 힌트**(`puzzle_hint`). 이미 푼 퍼즐이면 보류, 퍼즐 상한에 닿으면 보류 |
| `last_attempt` | 마지막으로 채점한 퍼즐 ID 일 뿐이다. 지금 그 퍼즐을 보고 있다는 뜻이 아니다 | **퍼즐을 짚지 않는 확인 발화**(`check_in`)만 |
| `none` | 대상을 정할 수 없다 | `check_in` 만 |

- **`check_in` 은 별도의 자동 개입 유형으로 승인됐다(2026-10-26).** 규칙은 §9 에 있다.
- 합성 데이터에는 FE 포커스가 없다. 그래서 모든 개입이 `check_in` 이 되고, **퍼즐당 상한은 합성 평가에서 작동하지 않는다.** 퍼즐 힌트 규칙(완료 퍼즐 금지 · 퍼즐 상한)은 손으로 만든 사례로만 검증했다(`test_p3b.py`).

## 3. 선택과 진단의 구분

| 구분 | 무엇으로 | 어디에 쓰나 |
|---|---|---|
| **지도 라벨 내부 검증 성능** | 안쪽 세션 GroupKFold 의 out-of-fold 점수. 모델 설정은 세션 가중 AP, τ 는 세션 가중 F1, 규칙 (a, b) 는 바깥 학습의 세션 가중 F1 | 모델·임계값 **선택** |
| **관측 가능한 행동 제한** | cooldown · 세션/퍼즐 상한 · ActivityGate | 정책 자체. 격자 전체를 **서술 보고**하고 고르지 않는다 |
| **숨은 상태가 필요한 사후 진단** | 탐색 10분당 불필요 개입 ≤ 1 · 활동 시간 차단률 ≤ 20% · 종료 후·away 개입 | **보고만** 한다. 못 맞추면 `feasible: false`. 맞춰도 `operational_suitability: not_assessed` |

- 선택 결과(`selection`)는 해시(`selection_sha256`)와 함께 남긴 **뒤에** 바깥 테스트를 한 번 평가했다. 바깥 테스트 결과를 보고 다시 고르지 않았다.
- 테스트로 확인했다: 바깥 테스트의 라벨과 특성을 망가뜨려도 선택이 같다.
- P3-A 와 달라진 점: 규칙 (a, b) 선택에서 예산 조건을 뺐다. 예산은 숨은 상태가 필요한 진단이라, 선택이 아니라 보고에만 둔다.

## 4. 평가 지표

- **분류** (라벨 있는 바깥 테스트 행 · 세션 가중)
  - Precision · Recall · F1 · AP · FDR · FPR · Brier
  - F1 · AP · P · R · Brier 는 세션 단위 부트스트랩 1,000회 95% 구간을 함께 낸다. 연속 tick 을 독립 표본으로 보지 않는다.
- **정책** (바깥 테스트의 모든 판단 시점 · 관측 가능 조건)
  - 탐색 10분당 · 활동 10분당 불필요 개입
  - 종료 후 개입 수와 비율, away 개입 수, 세션당 개입 수
  - 막힘 발견율, 첫 개입까지 시간, 차단 없음 대비 발견 손실
  - 보류 사유별 수, 개입 종류별 수
- **ActivityGate 진단** (모델과 무관)
  - 활동 차단률(전체 · 유형별, 특히 장시간 탐색형), 탐색 차단률
  - 종료 후 · away 탐지율, 차단 정밀도
- **이상 조건 참고**: working·exploring·stuck 시점만 쓰는 Oracle 필터 실행(기본 정책만).
- **generator_reference**: Oracle(유형)을 쓰는 참고 결과. 운영에 적용할 수 없고 상한선이 아니다.

## 5. ActivityGate 의 한계

- 이 차단은 종료 후 개입을 **줄일 뿐 없애지 못한다.** 종료 직후 cutoff 까지는 막지 못하고, cutoff 보다 짧은 자리 비움도 막지 못한다.
- **Oracle 없이 종료 후 개입을 완전히 막을 수 있다고 가정하지 않는다.**
- 실제 세션 종료·일시정지 이벤트는 backend 팀과 협의할 별도 계약 변경이다(합의 #19).

## 7. 발견한 문제

1. **로지스틱 회귀의 C 선택이 사실상 임의다.** 안쪽 AP 가 C 0.001~100 에서 0.4459~0.4481 로 거의 같았다. 고른 C 가 seed 마다 0.001~100 으로 흔들렸고, τ 와 F1 도 흔들렸다(case_001 F1 0.33~0.46).
2. **규칙 (a, b) 가 매번 격자 끝(a=2, b=240)에 붙었다.** P3-A(예산 조건 포함)와는 반대쪽 끝이다. F1 만으로 고르면 재현율 쪽으로 치우친다.
3. **LightGBM 은 분류 지표가 가장 좋았지만, 정책 진단은 6/9 에서 탐색 10분당 목표를 넘었다.** 분류 성능과 정책 성능이 같은 방향이 아니다.
4. **세션 상한과 막힘 발견이 정면으로 부딪힌다.** 상한 3회에서 발견율이 0.25~0.44 로 떨어졌다.
5. **2분 차단은 종료 후 위험을 크게 줄이지만 정상 장시간 탐색을 많이 막는다.** 5·10분은 학습 모델에 거의 효과가 없었다.
6. **퍼즐 힌트 경로는 합성 데이터로 평가되지 않았다.** FE 포커스가 없어서 모든 개입이 check_in 이었다.
7. **매개변수 이동에서 LightGBM 의 AP 가 더 많이 떨어졌다.** 생성 규칙 재학습 가능성을 배제할 수 없다.
8. **가중치 전략 간 차이는 통계적으로 구분되지 않았다.**

| `hint` (퍼즐 힌트) | 자동 | **확인된 현재 포커스**(`observed_focus`) + **서버 승인 콘텐츠** + 아직 안 푼 퍼즐 | 승인 힌트의 범위 | 승인 범위 밖의 내용 · 정답 |
| 요청 힌트 | **플레이어** | 플레이어가 직접 요청(`player_request`) | 승인 힌트의 범위 | 자동 개입과 같은 금지 |
| `nudge` | (P4 에서 정의) | 주의 환기 수준(npc_hint_level 1)의 방향 제시 후보 | P4-A 설계에서 정한다 | — |

- **횟수 제한**: `check_in` 도 세션당 상한(3회)과 cooldown(60초)에 포함한다. 퍼즐당 상한(2회)은 퍼즐 힌트에만 적용한다.
- **자동 개입과 요청 힌트는 다른 경로다.** 이 실험의 정책·상한은 자동 개입에만 적용한다. 요청 힌트의 횟수 규칙은 아직 정하지 않았다.
- **Hint API 와의 관계**: 기존 Hint API 계약(정적 2단계 힌트, `hint_levels`)은 바꾸지 않는다. NPC 는 그 단계를 바꾸지 않는다(docs/00 §4).
- **현재 한계**: P3-B 합성 평가에서는 퍼즐 힌트 경로가 **검증되지 않았다.** 모든 개입이 `check_in` 이었다.

### 9.2 모델

- LightGBM 과 로지스틱 회귀를 **모두 후속 실험 후보로 남긴다.** 이 결과만으로 운영 모델을 정하지 않는다.
- **LightGBM**: 세 사건 모두에서 분류 지표(F1 · AP · Brier)가 가장 좋았다(§6.1).
- **로지스틱 회귀**: 기본 정책에서 개입 빈도가 낮았다(세션당 0.5~2.0회 대 LightGBM 1.5~2.2회). 탐색 진단 목표를 맞춘 폴드도 더 많았다(8/9 대 3/9).
- **정책 고정값**: cooldown 60초 · 세션당 3회 · 퍼즐당 2회를 유지한다.
- **이번 바깥 테스트 결과를 보고 설정·임계값을 다시 조정하지 않는다.**
- **다음 실험용 결정 규칙**: 로지스틱 회귀 C 후보들의 안쪽 AP 차이가 0.002 이하이면, 그 안에서 **가장 작은 C**(가장 강한 정규화)를 고른다. 이번 실험에는 적용하지 않았다.

### 9.4 누설 검사 오탐과 개선 방향

- 오탐 사례: 커밋용 metrics.json 에서 가상 사건의 4자리 숫자 정답이 소수점 지표값(`inner_average_precision`) 안의 숫자열에서 잡혔다. P2-C 에서는 무작위 UUID 안에서도 같은 일이 있었다(docs/04 §6-6). **실제 누설은 아니다.**
- 검사를 끄거나 숫자 정답 검사를 없애지 않는다. 대신 검사 대상을 세 가지로 나누는 것을 개선 과제로 둔다.
  1. **구조화된 메타데이터**(식별자 · 모델 지표 · 해시 · 시각): 형식을 알고 있으므로 값 형식별로 검사한다. 예: 숫자 지표는 누설 대상에서 빼되, 문자열 필드는 그대로 검사한다.
  2. **NPC 가 실제로 쓰는 발화·지식 콘텐츠**(knowledge text · 승인 힌트 · 생성 발화): 지금처럼 정답과 별칭을 전부 검사한다. 오탐이 나더라도 막는 쪽을 택한다.
  3. **운영상 비공개 정답 정보**(server.json `accepted_answers`): 검사 기준으로만 쓰고 출력에 넣지 않는다.
- 출력 발화의 의미 수준 누설과 ID 노출 검사는 P4 에서 따로 한다.
