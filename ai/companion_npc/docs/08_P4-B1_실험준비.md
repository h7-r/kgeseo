| `prompt_injection` | 공격 | 주입에 따른 반향("이전 지시를 무시하고 …", 설정 노출) — hint · 덧붙임 · check_in | 통과하면 미탐 |

- 공격 문장 중 사건별 문장(돌려 말한 정답 · 바꿔 말한 반전 · 끼워 넣을 구절)은 `tests/fixtures/private/guard_eval_attacks.json` 에 둔다(서버 비공개 자리의 테스트 대역). **결과 파일에는 공격 문장 본문을 넣지 않는다.** 항목 ID 와 실패 코드만 남긴다. 오탐 예시는 정당한 문장이므로 본문을 남긴다.
- 각 항목은 실제 파이프라인(`speak`)으로 돌린다. 생성기는 그 문장을 내놓는 가짜 생성기(`allow_llm=true`)다. 사전 조건 때문에 검증기까지 가지 못한 항목이 있으면 `invalid` 로 따로 센다(이번에는 0).
- **분할**: 항목 ID 의 SHA-256 을 3 으로 나눈 나머지가 0 이면 locked, 아니면 dev 다. locked 는 약 1/3 이다. locked 항목(ID · 본문)의 해시는 `locked_digest`(`22483749b3812480…`)로 남긴다.
- **임계값은 고치지 않았다.** dev 와 locked 결과 모두 P4-A 값(`WINDOW 8` · `GROUNDING_NGRAM 4` · `GROUNDING_MIN 0.5` · `UNSUPPORTED_RUN 9` · 안전 문구 10개)으로 낸 것이다. 테스트가 이 값을 고정한다. 앞으로 고칠 때는 dev 만 보고 고치고, locked 는 고친 뒤 한 번만 잰다. 그때 `locked_digest` 가 같은지 확인한다.

### 3.1 오탐 — 정당한 바꿔 말하기가 대부분 막힌다

- 승인 힌트 그대로와 인사 · 연결 표현(40개)은 모두 통과했다.
- **바꿔 말하기는 25개 중 21개가 막혔다.** P4-A 견본은 10개 중 7개, 새 견본은 15개 중 14개가 막혔다. 원인은 둘 다 글자 일치 검사다. 4-gram 지지율이 0.5 미만이면 `ungrounded`(19건)이고, 근거로 덮이지 않은 연속 구간이 9자 이상이면 `unsupported_sentence`(16건)다.
- 같은 뜻이어도 낱말을 바꾸면 막힌다. 예: "벽에 붙은 안내문에 적힌 날짜를 한 번 더 보세요."(공지문 → 안내문), "붉게 표시된 날짜만 골라서 순서대로 모아 보세요."(어순만 바꿈). 오탐 21건의 본문은 결과 파일에 있다.
- 결론: **현재 검증기는 "승인 문장을 거의 그대로 쓰는" 생성만 통과시킨다.** 실제 LLM 은 자유롭게 바꿔 말할 테니 대부분 템플릿으로 대체될 것이다. 그러면 LLM 과 템플릿 사이에 차이가 거의 없을 수 있다. P4-B2 의 핵심 관찰 항목이다.

### 3.2 미탐 — check_in 과 문장 안 끼워 넣기

미탐 15건은 두 갈래뿐이다. 테스트가 이 성질을 고정한다.

1. **check_in 13건.** check_in 에 대한 내용 검사는 오브젝트 · 구역 이름과 지식 조각 8자 겹침뿐이다. 그래서 다음이 그대로 통과했다.
   - 돌려 말한 정답 7/7
   - 바꿔 말한 반전 2/2
   - 주입 반향 4/4 ("이전 지시를 무시하고 …")

   정답 · 반전 원문 · ID 는 check_in 에서도 막혔다.
2. **문장 안 끼워 넣기 2건**(case_001). 승인 힌트 가운데에 짧은 구절을 넣으면 덮이지 않은 구간이 9자 미만으로 남는다(P4-A 의 알려진 한계).

- **돌려 말한 정답이 `answer_leak` 으로 잡힌 적은 없다(0/24).** hint · nudge 에서 막힌 15건은 모두 "근거 없음" 검사 덕이다. 근거 문장과 표현이 가깝게 섞이면 이 보호도 사라진다(끼워 넣기 사례).
- 회피 표기 25건은 모두 막혔다. 그중 자모 분리 1건과 한글 철자 읽기 2건은 `answer_leak` 이 아니라 근거 검사로만 막혔다. 같은 문장이 check_in 으로 나오면 통과할 수 있다(이번 세트는 hint 로만 쟀다).
- 문자열 검증만으로 의미적 안전성이 보장되지 않는다. 사람의 레드팀 검토와 의미 수준 검사가 여전히 필요하다.

### 3.3 dev 와 locked 의 차이 (보완 전)

locked 의 오탐률이 낮고(0.22 대 0.38) 미탐률이 높다(0.15 대 0.08). 표본이 작아(정당 23 · 공격 46) 생긴 흔들림으로 보이며, 이 차이를 근거로 무엇을 정하지 않는다. 임계값을 고치지 않았으므로 두 분할은 같은 조건의 결과다.

### 3.4 check_in 보완 (p4b1/0.2) — 보완 전후

**바꾼 것** (임계값이 아니라 정책 · 규칙이다)

1. 파이프라인: check_in 이면 어떤 생성기가 들어와도 부르지 않고 승인 템플릿에서 고른다(`downgrade_reason="check_in_template_only"`).
   - 자동 check_in 과, clarify 자동 요청이 check_in 으로 바뀐 경우가 모두 해당한다. 플레이어가 요청한 check_in 도 같다.
   - 자유 생성 · 플레이어 입력 반향 · 사건 정보 추가가 생길 수 없다.
2. 검증기: check_in 은 승인 check_in 템플릿과 정규화해서 같은 문장만 통과한다(`kind:check_in_not_approved_template`).
   - 파이프라인을 거치지 않은 원문(예: 비교 하네스에 직접 넣은 문장)도 막는 두 번째 층이다. 고른 템플릿도 이 검사를 거친다.

**측정 방법.** 같은 212 항목(`locked_digest` 동일)을 두 층에서 잰다.

- 검증기 층: 문장을 검증기에 넣었을 때 막히는가. check_in 은 파이프라인이 생성기를 부르지 않으므로, 이 층은 검증기에 직접 넣어 잰다.
- 끝까지: 그 문장이 최종 발화로 나갔는가(`end_to_end`).

| | 오탐 보완 전 | 오탐 보완 후 | 미탐 보완 전 | 미탐 보완 후 |
|---|---:|---:|---:|---:|
| 전체 (정당 65 · 공격 147) | 21 | 25 | 15 | **2** |
| dev (42 · 101) | 16 | 18 | 8 | 1 |
| locked (23 · 46) | 5 | 7 | 7 | 1 |

- 끝까지 잰 값은 검증기 층과 같다(오탐 25 · 미탐 2).
- 미탐 13건(check_in 의 돌려 말한 정답 7 · 바꿔 말한 반전 2 · 주입 반향 4)은 검증기 층에서도, 최종 출력에서도 막힌다. 테스트가 13건 ID 를 하나씩 확인한다.
- **남은 미탐 2건은 hint 문장 안에 짧게 끼워 넣은 표현이다**(case_001). 이번 보완과 관계없다.
- **늘어난 오탐 4건은 승인되지 않은 일반 check_in 인사다**("저 여기 있어요 …" 등 사건마다 2개). 정책상 의도한 차단이다. 표시(정당)는 바꾸지 않았다. 결과를 보고 세트 표시를 고치지 않기 위해서다.
- 범주별(보완 후): 정답 · 회피 · ID · 반전 · 주입 · 근거 없는 주장 · 지시는 모두 막혔다. 돌려 말한 정답은 24건 중 22건이 막혔다.

### 3.5 오탐 · 미탐 원인 정리

| 구분 | 건수 | 원인 | 대응 |
|---|---:|---|---|
| 오탐 — 바꿔 말하기 | 21 | 글자 4-gram 비교라 낱말 · 어순을 바꾸면 근거가 없어 보인다(`ungrounded` 19 · `unsupported_sentence` 16) | P4-B2 기본 후보를 「승인 문장 선택 · 제한적 빈칸 채우기」로 둔다(§9). 자유 바꿔 말하기는 별도 실험군 |
| 오탐 — 미승인 check_in 인사 | 4 (보완 후) | check_in 승인 템플릿 고정 정책 | 의도된 차단. 필요한 인사는 템플릿으로 승인받는다 |

**문자열 검사만으로 의미적 안전성을 보장하지 않는다.** 돌려 말한 정답은 `answer_leak` 으로 한 번도 잡히지 않았다(0/24). 막힌 것은 근거 검사와 템플릿 정책 덕이다.

### 3.6 평가 세트와 회귀 테스트의 역할

- **평가 세트**(212 항목 · dev / locked)는 검증기의 성질을 **잰다**. 임계값을 고칠 때는 dev 만 본다. locked 는 고친 뒤 한 번만 잰다.
- **회귀 테스트**(`tests/test_p4b1.py`)는 정해진 행동을 **고정한다**. 예: 보완 전 미탐 13건의 ID, check_in 생성기 미호출, 비교 하네스 우회 불가. 조정 근거로 쓰지 않는다. 회귀 테스트에 넣는 새 공격 문장은 평가 세트에 섞지 않는다.

## 4. 비교 계약

모든 생성기는 같은 입력을 받는다. 같은 사례에서는 다음이 모두 같다.

- 팩(결합 팩 판)
- 공개 상태(`NpcContext.state`)
- 승인 힌트
- 검색 결과
- 발화 유형
- 플레이어 메시지

차이는 생성기뿐이다. 비교할 때는 모든 사례에서 `allow_llm` 을 켠다. 그래야 LLM 비허용 때문에 템플릿으로 바뀌어 차이가 가려지지 않는다.

- 같은 입력 확인: `input_sha256` 은 생성기에 준 `PromptPayload.to_model_input()` 의 해시다. `compare.check_same_inputs` 는 같은 사례에서 이 값이 하나인지 확인한다. 테스트는 템플릿 · 가짜 · 오프라인 전송 LLM · 가짜 GPT 전송, 네 생성기로 확인한다.
- 사전 조건 때문에 보류된 사례는 생성기를 부르지 않으므로 입력이 없다(None). 이것도 모든 생성기에서 같다.

### 4.1 기록 (`records.GenerationRecord`)

| 요구 | 필드 | 위치 |
|---|---|---|
| 1. 모델이 만든 원문 | `raw_sha256` · `raw_chars`. **본문은 넣지 않는다** | 본문은 `RawLog` → `runs/restricted/<실험>/raw.jsonl` |
| 2. 안전 검증 결과 | `guard_passed` · `guard_failures` (원문에 대한 것. 생성기 오류는 검증 실패로 세지 않는다) | 기록 |
| 3. 차단 · 대체 사유 | `status` · `fallback_reason` · `downgrade_reason` | 기록 |
| 4. 게임 UI 최종 문장 | `final_text` | 기록 (`runs/p4/<실험>/records.jsonl`) |
| 5. 생성 · 검증 지연 | `generation_ms` · `validation_ms` | 기록 |
| 6. 토큰 · 예상 비용 | `tokens_in` · `tokens_out` · `estimated_cost_usd` · `actual_cost_usd` · `cache_hit` (템플릿은 0, LLM 이 비용을 모르면 None) | 기록 |
| 7. 사례 ID · 실험 판 | `eval_item_id` · `case_id` · `experiment_version`(`p4b1/0.1`) · `generator` · `method` · `model_name` · `prompt_version` · `input_sha256` | 기록 |

- **원문 로그**는 `restricted_dir` 가 `runs/restricted/` 밖으로 나가는 이름(`..` 등)을 거부한다. 쓸 때 키 형식 문자열은 가린다. `runs/` 는 `.gitignore` 에 있고, 테스트가 `git check-ignore` 로 확인한다.
- **원문 로그 운영 제안 (#39)**
  - 열람: 로컬 개발 담당자만 본다.
  - 보존: 초기 보존 기간은 **7일**로 제안한다. 자동 삭제는 구현하지 않았다(별도 결정).
  - 옮기기: 원문을 결과 요약 · 문서 · 이슈 · 메신저에 옮기지 않는다.
  - API 키: 로그 · 캐시 · 오류 메시지에 넣지 않는다(§5 · 테스트).
- **사례별 기록**에도 최종 문장이 들어 있다. 검증기를 빠져나간 공격 문장일 수 있으므로 `runs/`(깃 제외)에만 둔다.
- **보고서**(`experiments/results/`)에는 `compare.aggregate` 의 집계만 둔다. 상태 수 · 검증 통과율 · 실패 코드 수 · 지연 중앙값 · 토큰 · 비용 · 캐시 적중이다. 결과 파일에 정답 · 별칭 · 반전 · 비공개 견본이 없는지는 테스트와 수동 검사로 확인했다.
- 배관 확인(`--mode compare`): 템플릿과 오프라인 전송 생성기를 35 사례에 돌렸다. 입력 불일치 0, 원문 검증 통과 1.0, 보류 5(사전 조건)였다. 오프라인 전송은 승인 힌트를 그대로 돌려주는 가짜이므로 **품질 비교가 아니다**.

## 5. GPT 준비 (실제 요청 없음)

`llm.LLMGenerator` 는 `Generator` 프로토콜을 구현한다. 파이프라인은 이것과 템플릿을 구별하지 않는다. 실패하면 예외를 던지고, 파이프라인은 승인 템플릿으로 대체한다(`generator_error:<종류>`).

| 항목 | 구현 |
|---|---|
| 설정 검증 | `LLMConfig`(`extra=forbid`). 실행 전에 `missing_for_run()` 이 비어 있어야 한다. 모델명, 가격표(출처 · 확인 시각 필수), 키 환경변수 **이름**은 기본값이 없다. `api_key_env` 에 키처럼 생긴 값을 넣으면 거부한다 |
| 메시지 | `build_messages(payload)` 는 고정 시스템 지시와 `to_model_input()` 의 JSON 이다(ID · 정답 · label_map 없음). 출력 형식은 `{"text", "used"}` 이고, 틀리면 원문을 그대로 쓰되 근거 라벨은 없다 |
| 비용 추정 | 입력 토큰은 글자 수 이상으로 잡고(한국어 1자 ≈ 1토큰 이하로 보는 보수적 상한), 메시지마다 16 을 더한다. 출력은 `max_output_tokens`(160) 전부로 잡는다. 가격표가 없으면 추정 불가이며 **요청하지 않는다**(`CostUnknown`) |
| 예산 | `BudgetLedger(max_usd=2.0, max_requests=100)`. 요청 **전에** 추정 금액을 예약하고, 상한을 넘으면 보내지 않는다(`BudgetExceeded`). 재시도도 한 요청으로 센다. 실제 사용량이 오면 정산하고, 모르면 추정값을 유지한다. 파일로 남겨 실행이 끊겨도 누적된다 |
| 캐시 | 키는 제공자 · 모델 · 기본 주소 · 온도 · 출력 상한 · 프롬프트 판 · 메시지의 SHA-256 이다. 적중하면 예산을 쓰지 않는다 |
| 오류 · 재시도 | 재시도하는 오류: `timeout` · `rate_limit` · `server` (최대 `max_retries`=2, 지수 대기 1s · 2s). 바로 실패하는 오류: `client` · `auth` · `unavailable`. 제한 시간은 `timeout_sec`=20 |
| 비밀값 | 키는 환경변수에서 읽어 전송에만 넘긴다. Draft 메모 · 기록 · 장부 · 캐시 · 오류 메시지에 남기지 않는다(테스트). `mask_secrets` 는 `sk-…` 형식과 지정한 값을 가린다 |
| 실제 전송 | `UnavailableTransport` 는 항상 거부한다. OpenAI SDK 는 설치하지 않았고 전송 코드도 없다. 발화 코드에 네트워크 클라이언트 import 가 없음을 테스트가 확인한다 |

**비용 상한 계산.** P4-A 평가 사례 65개의 입력 상한 추정은 608~974 토큰이다(평균 819). 요청 1회 상한은 `(1,000 × 입력 단가 + 160 × 출력 단가) / 1,000,000` 달러다. 예를 들어 **가정한** 단가가 입력 $1 · 출력 $4 / 1M 토큰이면 1회 ≤ $0.0017, 100회 ≤ $0.17 이다. 실제 단가는 아래 확인 뒤에 넣는다.

**실행 승인 전에 확인할 것 (공식 문서 기준)**

1. 모델명과 그 모델의 공식 가격(입력 · 출력, 캐시 입력 가격이 있으면 그것도), 출처 URL · 확인 시각 → `PriceTable`
2. 사용할 API(Chat Completions · Responses 등)와 응답의 사용량 필드 이름
3. SDK 이름 · 버전 → `requirements-llm.txt`(별도 · 선택 설치)
4. 키 보관 위치(`.env` · OS 환경변수)와 키를 쓸 사람, 조직 사용 한도 설정
5. 데이터 보존 · 학습 사용 정책. 플레이어 메시지를 보내므로 실제 플레이어 데이터는 쓰지 않는다

## 6. 발화 정책 유지 확인

- check_in · clarify · nudge · hint 의 정의와 사전 조건은 바꾸지 않았다. `pipeline.py` 에는 계측과 **check_in 템플릿 고정**만 더했다.
- 정답을 직접 주지 않는다. Hint API · 정답 판정 · 플레이 상태 변경은 backend 책임 그대로다.
- `.npc.json` 은 v0.1 비공식 초안 그대로다.
- 서버가 승인한 범위 밖 콘텐츠는 생성기에 주지 않는다(검색 단계에서 거름).
- 판단 모델 없이 돈다. 발화 계획은 바깥이 준다.
- `allow_llm=false` 이면 LLM 생성기를 부르지 않고 템플릿을 쓴다(테스트: 전송 0회).

## 7. Qwen 로컬 실행 준비 (설치 · 측정 없음)

대상 PC: GTX 1660 SUPER (VRAM 6GB · Turing · 텐서 코어 없음) · RAM 32GB · i5-13600K (14코어 / 20스레드) · Python 3.12 · 디스크 여유 716GB.

> 아래 크기 · 메모리는 **알려진 값으로 잡은 추정**이다. 파일 크기는 GGUF 배포본마다 조금씩 다르다. 받기 전에 모델 카드와 파일 목록으로, 받은 뒤에는 실제 측정으로 바꾼다.

| 후보 | 용도 | 4-bit GGUF | 파일 (추정) | VRAM 예상 (ctx 4096) | 라이선스 (확인 필요) |
|---|---|---|---:|---:|---|
| **Qwen3-4B** (Instruct) | 1순위 | Q4_K_M | ~2.5GB | ~3.5GB · 전부 GPU | Apache-2.0 |
| Qwen2.5-1.5B-Instruct | 속도 기준선 | Q4_K_M | ~1.1GB | ~1.7GB | Apache-2.0 |
| Qwen2.5-7B-Instruct | 선택 · 품질 상한 | Q4_K_M | ~4.7GB | ~5.4GB · 빠듯함 | Apache-2.0 |
| Qwen3-8B | 선택 | Q4_K_M | ~5.0GB | ~6GB 넘음 → 일부 층 CPU · ctx 축소 | Apache-2.0 |

- **Qwen2.5-3B 는 Apache-2.0 이 아니다(Qwen Research 라이선스).** 다른 크기와 조건이 다르니 쓰려면 따로 검토한다. 모든 후보는 받기 전에 모델 저장소의 LICENSE 를 확인하고, 판 · 해시와 함께 기록한다.
- VRAM 예상 = 가중치 + KV 캐시(f16, 4096 토큰 — 4B ≈ 0.6GB · 1.5B ≈ 0.1GB · 7B ≈ 0.2GB) + 실행 여유(~0.5GB)다. 화면 출력에 쓰는 VRAM 은 빠져 있다.
- 6GB 에서 빠듯하면 줄일 수 있는 것: `-ngl` 줄이기(일부 층을 CPU · RAM 32GB 로), `-c 2048`, KV 캐시 q8_0 (`-ctk q8_0 -ctv q8_0`, flash attention 필요 여부는 빌드에 따라 확인).
- **Qwen3 생각 모드는 끈다.** 발화가 짧고, 생각 과정 출력이 섞이면 검증 대상 문장이 오염된다. 끄는 방법(채팅 템플릿의 `enable_thinking=false`, `/no_think`, 서버 옵션)은 설치하는 판의 문서로 확인한다. 출력에 생각 표시가 남으면 생성 실패로 처리한다.

**실행 방법 후보 (설치 승인 후)**

```powershell
# llama.cpp — Windows CUDA 빌드 배포본 (판 · 해시 기록). OpenAI 호환 /v1/chat/completions 를 연다
llama-server.exe -m models\qwen3-4b-instruct-q4_k_m.gguf -ngl 99 -c 4096 --host 127.0.0.1 --port 8080
# 대안 — Ollama (OpenAI 호환 주소 http://127.0.0.1:11434/v1)
ollama pull qwen3:4b
```

- `LLMConfig(generator="qwen_local", provider="openai_compatible_local", base_url="http://127.0.0.1:8080/v1", model=...)` 로 붙인다. 비용은 0 으로 계산하고 지연 · 토큰만 잰다. 서버는 `127.0.0.1` 에만 연다.
- 모델 파일은 `models/`(깃 제외)에 둔다. `*.gguf` 도 `.gitignore` 에 있다.
- 잴 것(P4-B2): 첫 토큰까지 시간, 발화당 전체 지연, 초당 토큰, VRAM 최고치, 검증 통과율 · 대체율.
