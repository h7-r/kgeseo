# 팀 합의 필요 사항 (v0.1 초안 기준)

| # | 질문 | 이 초안의 가정 | 관련 |
|---|---|---|---|
| 1 | NPC 힌트 수준(`npc_hint_level`)을 backend `hint_levels` 와 **다른 축**으로 두는 데 동의하는가 | 다른 축. NPC 는 2에서도 정답 비노출, `hint_levels` 를 바꾸지 않음 | 파이프라인 설계요청 §4.6 은 `hint_level 2 = 정답 공개` |
| 2 | 승인 힌트·지식 조각(`ApprovedHint`, `KnowledgeChunk`)을 누가 쓰고, 어디에 저장하나 | 사람 승인. 저장 위치 미정 | PRD USR-108, 파이프라인 §5.3 |
| 3 | Case ID 규칙: backend `case_001` vs 파이프라인 문서 `case-naju-01` | 둘 다 `CASE_ID_PATTERN` 통과. 실제 값은 backend 를 따름 | |
| 4 | GameSpec / PuzzleSpec(CompiledPuzzleSpec) 스키마는 누가, 언제 확정하나 | 없음 → ScenarioPack 은 client/server JSON 에서 만들 수 있게 설계 | PRD ADM-090, origin/dev 설계요청 v2.1 |
| 5 | Clue registry(단서 ID 목록·표시 문구)의 원천 | ScenarioPack `clues[]` 에 둠 | case_content_zone_mapping §9 Contract Gap |
| 6 | NpcContext 를 누가 조립하나: 별도 NPC 서비스 vs backend 안 | 별도 프로세스, backend 는 읽기만 | |
| 7 | `answer_fingerprint` 를 backend 가 만들어 줄 수 있나 (정규화 답 + 세션 salt 해시) | 제안만. 없으면 피처에서 뺌 | interaction_events 에 원문 payload 가 저장됨 |
| 8 | npc-follow 프로토타입과의 연결 방식 (이벤트 → NPC 서비스 호출 → 대화창) | 실험 단계에서는 연결하지 않음 | origin/feat/SJ-npc-follow-prototype (담당 SJ) |
| 9 | 누설 검사의 별칭(예: VALVE ↔ 밸브) 목록을 누가 관리하나 | 사람이 정함. 글자 비교만 하므로 의미 검사는 P4 에서 별도 | spoiler.py |
| 10 | 실험용 플레이 로그를 운영 DB 에서 내보내도 되나 (개인정보·익명 세션) | 합성 데이터로 시작, 내보내기는 합의 후 | PRD CMN-030 |
| 11 | `ai/companion_npc/` 위치와 루트 `.gitignore` 를 그대로 둘지 | 루트는 안 고치고 이 폴더 안 `.gitignore` 사용 | 브랜치-작업규칙 §5 |
| 12 | (P2-A) input 이외 interaction 의 `target_id` 가 무엇을 가리키나 (inspect → clue? navigate → zone?) | 퍼즐로 보지 않고 옮기지 않음 | case_content_zone_mapping §9 |
| 13 | (P2-A) 효과(`complete_puzzle_ids`)에만 나오고 `puzzles[]` 에 없는 퍼즐 ID 를 허용하나 | 허용하고 경고 | backend 는 검사하지 않음 |
| 14 | (P2-A) 처음에 숨은 물건(`visible=false`)이 드러나는 조건을 어디에 정의하나 | 정의 전까지 NPC 지식에서 제외 | Contract Gap |
| 15 | (P2-A) ID 이름에 이야기 정보를 담지 않는다는 명명 규칙을 둘지 (예: `CLUE_KEEPER_TRUTH`) | 발화층은 ID 를 문장에 쓰지 않음 | PRD ADM-097 명명 규칙 |
| 16 | (P2-A) 정답 별칭(VALVE ↔ 밸브) 목록의 저장 위치 — server.json 에 둘지, 별도 파일로 둘지 | CLI `--alias` 로만 받음 | spoiler 한계 |
