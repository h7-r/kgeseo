## 0. 한눈에 보는 구성

```text
                         [ Cloudflare DNS ]  ← 도메인 구입 · 관리 (AWS 계정과 분리)
                          │  (모든 레코드 DNS only · 회색 구름)
     ┌────────────────────┼─────────────────────────┬───────────────────────┐
     ▼                    ▼                         ▼                       ▼
 www.도메인           play.도메인               api.도메인              lobby.도메인
 웹사이트(SPA)        게임 본편 + 나주(SPA)      FastAPI                Colyseus 로비
 Vercel               Vercel                    ┐                       ┐
                                                ├─ EC2 t4g.medium 1대 (Caddy가 HTTPS 처리)
                                                ┘                       ┘
                                                        │ 사설망(3306)
                                                        ▼
                                                 RDS MySQL 8.4 (비공개)

 게임이 쓰는 무거운 파일 ──→  S3 게시 버킷 ──→ CloudFront (xxxx.cloudfront.net)
 공용 라이브러리 전체   ──→  미르 맥(원본) ⇄ S3 라이브러리 버킷(비공개 · 나중에)
 AI 제작 공정          ──→  미르 맥 + GIST GPU(12월까지) · 1월 이후 Meshy/Tripo API · 대량은 GPU 임시 임대
```

- **브라우저가 3D를 그린다.** 서버는 판정 · 저장 · 위치 같은 작은 JSON만 다룬다. 그래서 서버 한 대로 베타가 된다.
- **무거운 파일은 CDN이 보낸다.** 몰림의 대부분인 「첫 접속 에셋 다운로드」를 앱 서버가 지지 않는다.
- **로비와 게임은 분리한다.** 로비가 꺼져도 혼자 플레이는 된다.
- **도메인 · 화면 · 서버 · 파일을 각각 다른 곳에 둔다.** 하나를 옮겨도 나머지는 그대로다(나중에 국내 클라우드로 옮길 때 핵심).

## 2. 무엇을 어디에 두는가 — 그리고 왜

### 2.1 도메인 · DNS — Cloudflare 🟢(구입) / 🟡(세부)

| 무엇 | 어디 | 왜 | 왜 가능한가 |
|---|---|---|---|
| .com 도메인 1개(또는 .kr을 국내에서 사고 네임서버만 Cloudflare) | Cloudflare Registrar + Cloudflare DNS | 가장 쌈(연 $10.46, 연장도 같음) · DNS 무료 · **AWS 계정과 분리** — AWS 계정 상태(무료 플랜 6개월 · 국내 클라우드 이전)와 상관없이 주소가 유지됨 | DNS 레코드는 IP나 이름만 가리키므로, 서버를 어디로 옮겨도 레코드만 바꾸면 됨 |

- 무료 도메인(kro.kr 등)을 쓰지 않는 이유: 인증서 발급 한도를 남들과 같이 씀(9월 Creed 때 실제로 걸림) · 연장 관리(ainews.kro.kr 만료 전례) · 하위 주소 지원 불확실 · 공용 상위 이름이라 쿠키가 덜 안전 · 지자체에 보여 줄 주소로 약함.
- **모든 레코드는 DNS only(회색 구름).** Cloudflare 프록시(주황 구름)를 켜면 Vercel 인증서 · Caddy 자동 인증서 · 로비 웹소켓이 꼬일 수 있다.
- 자동 연장을 켠다.

### 2.2 화면 — Vercel 🟢

| 무엇 | 어디 | 왜 | 왜 가능한가 |
|---|---|---|---|
| 웹사이트 SPA(`website/`, `npm run web:build`) | Vercel → `www.도메인` 🟡 | 이미 쓰는 곳 · push하면 자동 배포 · 무료 | 정적 파일이라 서버가 필요 없음 |
| 게임 본편 + 나주(루트 `npm run build`, `index.html` + `naju01/index.html`) | Vercel → `play.도메인` 🟡 | 위와 같음 | 위와 같음. 나주는 본편 빌드 안의 `/naju01/` |

- 웹사이트와 게임은 **서로 다른 주소**다. 코드에 이미 `VITE_GAME_URL`(웹사이트 → 게임)과 `VITE_SITE_URL`(게임 → 웹사이트)이 있다.
- 🔴 **웹사이트가 지금 Vercel에 따로 배포돼 있는지 확인 필요(해랑 님).** Vercel 프로젝트 `kgeseo`는 루트(게임)를 빌드한다. 웹사이트는 두 번째 Vercel 프로젝트(Root Directory `website`)가 필요할 수 있다. 무료 플랜도 프로젝트 200개까지 된다.
- Vercel 프로젝트는 해랑 님 개인(Hobby) 계정 → 멤버 초대 불가 → **값은 미르가 정하고 해랑 님이 넣는다** 🟢.
- 무료 플랜 조건: 월 전송 100GB · 비상업 용도. 무거운 에셋을 CDN으로 빼서 전송량 문제를 없앤다. 지자체 납품 · 유료 운영 단계에서 Pro 또는 이전을 다시 정한다.

### 2.3 API 서버 · 로비 서버 — EC2 1대 🟢

| 무엇 | 어디 | 왜 | 왜 가능한가 |
|---|---|---|---|
| FastAPI(`backend/`) · 사건 서버 JSON · NPC 실행부 | EC2 t4g.medium(2vCPU · 4GiB, ARM) · 서울 | 상시 켜진 서버가 필요(서버 기준 판정 · 멱등 · 세션). Vercel 함수로는 맞지 않음 | 의존성(`requirements.txt`)이 모두 ARM에서 설치됨 · 팀 배포 초안(`backend/docs/deployment_aws_v0.1.md`)과 같은 구성 |
| Colyseus 로비(새로 만들 것) | 같은 EC2, 별도 프로세스 | 정원 · 방 생성 · 재접속이 기본 기능이라 직접 만들 부담이 줄어듦 | 50동접 위치 동기화는 초당 약 2.2Mbps · 메시지 초당 약 1,000건 수준(가정치, [미측정]) |
| Caddy | 같은 EC2 | `api.` `lobby.` 두 주소의 HTTPS · WSS 인증서를 자동 발급 · 갱신 | 도메인이 EC2 고정 IP를 가리키면 Let's Encrypt가 자동 처리 |

- **고정 IP(Elastic IP)를 꼭 붙인다.** 안 붙이면 재시작 때 IP가 바뀌어 DNS가 틀어진다. 비용은 공인 IPv4 월 $3.65에 이미 포함.
- 프로세스 관리: systemd로 FastAPI(uvicorn) · 로비(node) 두 서비스를 등록 → 서버가 재부팅돼도 자동으로 다시 뜬다 🟡.
- 열어 둘 포트: 80 · 443만(인터넷 전체). SSH(22)는 미르 IP만 또는 아예 닫고 AWS Systems Manager 접속 🟡.
- 🟡 **CPU 모드(standard / unlimited)는 부하 시험 뒤에 정한다.** standard는 크레딧이 떨어지면 느려지고, unlimited는 초과분이 과금된다. 그 전까지는 예산 알림으로 막는다.

### 2.4 DB — RDS MySQL 🟢

| 무엇 | 어디 | 왜 | 왜 가능한가 |
|---|---|---|---|
| 플레이 기록 · 세션 · 승인 기록 · 힌트 잔액 등(마이그레이션 18개) | RDS MySQL 8.4 · db.t4g.micro · Single-AZ · 20GB · 자동 백업 | 베타 기록(완주율 · 이탈 단계)이 12월 발표 근거 → 자동 백업 · 시점 복구가 필요 · EC2에 같이 올리면 장애 · 자원 경합 · 백업 책임이 같이 옴 | 코드가 표준 MySQL + Alembic이라 그대로 붙음 |

- **퍼블릭 접근 끔.** 3306 포트는 EC2 보안그룹에서만 받는다.
- 앱 계정은 root가 아닌 전용 계정(`DB_USER`).
- MySQL 8.4로 시작(8.0은 2026년 8월부터 Extended Support 추가 과금 대상).
- **백업은 복구 시험을 한 번 해야 의미가 있다.** 복구본 DB를 만들어 테이블 수 · 기록 수를 대조한다.
- 위치 갱신(로비)은 DB에 쓰지 않는다.

### 2.5 게임 에셋 — S3 게시 버킷 + CloudFront 🟢

| 무엇 | 어디 | 왜 | 왜 가능한가 |
|---|---|---|---|
| 게임이 실제로 쓰는 무거운 파일: `public/models`(153MB) · `public/transitions`(59MB) · manifest와 코드가 부르는 `_sf_local` 파일 · 웹사이트 영상(159MB) | S3 게시 버킷(예: `waegok-assets`, 비공개) → CloudFront로만 공개 | 첫 접속 1인 약 100~250MB(추정, [미측정]) × 100명 = 10~25GB를 Vercel 무료 한도에서 빼기 · CloudFront **종량제 요금의 무료 사용 구간**(월 1TB · 1천만 요청 — 정액형 Free 플랜과 한도가 다름) 안 | 코드가 에셋 주소를 `VITE_ASSET_BASE` 하나로 만들게 바꾸면(해랑 님 적용) CDN 주소로 바뀜 |

- **CloudFront 기본 주소(`xxxx.cloudfront.net`)를 그대로 쓴다** 🟡. 에셋은 쿠키가 필요 없어서 자체 도메인이 필요 없고, 인증서 발급이 하나 준다.
- S3는 직접 공개하지 않고 CloudFront만 읽게 한다(OAC).
- GLB를 불러오려면 CORS 허용(`play.도메인`, `www.도메인`).
- 파일 이름은 그대로(manifest가 `/_sf_local/…` 경로로 부르므로) 둔다. `VITE_ASSET_BASE`는 **CDN 기본 주소만** 담고, 케이스별 게시 버전 경로(예: `/c/<case_id>/v<버전>/`)는 **게시 데이터가 정한다**(12.1) — 진행 중인 플레이어가 새 판 게시 뒤에도 자기 판의 파일을 계속 읽게 하기 위함.
- **올리는 기준은 「라이선스 값」.** `license.type`이 허용 목록(CC-BY 등)에 있는 것만. KHS 저작권 표기 파일 1개 · 유니티 에셋스토어 원본은 올리지 않는다. CC-BY는 출처 표기 화면이 필요하다.

### 2.6 공용 라이브러리(안 놓인 에셋 포함) — 맥 원본 + 비공개 버킷 🟡

| 무엇 | 어디 | 왜 | 왜 가능한가 |
|---|---|---|---|
| 라이브러리 전체(GLB + `asset.json` + 색인) | 원본: 미르 맥 `~/flux-test/public3d/library` / **베타 중 바로 비공개 원격 백업**(원본 · 색인 · 메타데이터 · 출처 · 검수 기록까지 복구 가능하게): S3 라이브러리 버킷(예: `waegok-library`, 비공개, 팀원 권한으로만) | 새 맵을 만드는 AI 에이전트 · 검수 도구 · 편집 모드는 **로컬 라이브러리**를 읽음. 플레이어 배포와 무관 | `tools/review/library.mjs` · `libraryPlacePlugin`(개발 서버 전용)이 로컬 파일을 읽는 구조 |

- 「미사용 `lib` 정리」 = **빌드에서 제외**이지 삭제가 아니다. 지우면 검수 도구 · 편집 모드가 깨진다.
- 게시할 때만: manifest에서 쓰는 목록 추출 → 라이선스 검사 → 라이브러리에서 게시 버킷으로 같은 경로로 복사(게시 판 폴더 아래). 세진 님 게시 CLI 뒤에 붙인다 🟡.
- 나중에(베타 이후) `public/_sf_local/lib`를 git에서 빼고 라이브러리 버킷 동기화 폴더로 옮긴다. 먼저 나주 퍼즐 3곳의 직접 참조를 게시 경로로 바꿔야 한다.
- 비용: 2.5GB 보관 월 약 $0.06 · 50GB여도 월 약 $1.25.

- Meshy · Tripo 결과물은 요금제에 따라 라이선스가 다를 수 있다 → `asset.json` `license.type`에 정확히 기록.

### 2.9 CDN에 올린 에셋과 새 게임 생성의 관계 🟢(원칙) / 🔴(확인 1건)

- **CDN은 복사본이다. 원본은 옮기지 않는다.**
  - 게시 버킷 · CloudFront에 올리는 것은 플레이어에게 보내기 위한 **복사본**이다.
  - 원본은 그대로 남는다: 저장소 `public/models` · `public/transitions` · `public/_sf_local` 그리고 공용 라이브러리(미르 맥 `~/flux-test/public3d/library`).
  - 「CDN으로 뺀다」 = 플레이어 배포 빌드에서 그 파일을 빼고 CDN 주소로 부르게 바꾸는 것이지, 저장소나 라이브러리에서 지우는 것이 아니다.
- **새 게임(새 맵)을 만들 때는 CDN이 아니라 원본을 읽는다.**
  - AI 에이전트 · 검수 도구(`tools/review`) · 편집 모드(`libraryPlacePlugin`)는 로컬 라이브러리 색인과 `asset.json`을 보고 고르고, 로컬 GLB를 불러와 배치한다.
  - 그래서 이미 다른 맵에 쓰여 CDN에 올라간 에셋도, 아직 아무 데도 안 놓인 에셋도 똑같이 다시 쓸 수 있다.
- **새 맵을 게시할 때:** 그 맵의 manifest가 쓰는 에셋 중 CDN에 아직 없는 것만 추가로 올린다(같은 게시 경로 안에서는 재업로드를 줄일 수 있으나, 새 게시 폴더를 만들면 같은 파일도 따로 저장될 수 있다 — 베타 규모에선 용량이 작아 감수, 커지면 내용 해시 기준 공용 저장으로 정리).
- **에이전트가 다른 곳에서 돌 때**(GIST · AWS 등): 그 서버가 라이브러리 버킷을 읽을 권한을 받아 동기화하면 같은 방식으로 동작한다. 공개 CDN을 제작용으로 쓰지 않는다.
- **11/5 대조 결과(정정판):** 에이전트가 고르는 목록은 `~/flux-test` 색인이 아니라 게임 저장소 검수 작업대의 `buildLibrary()`이고, 여기에 `lib` 955 · `khs` 105 · 나주맵 공개 경량본 80 · `codeprops` 42가 모두 들어 있다(배치 가능 1,182개). 그래서 khs · 자연물 · 코드 소품은 **이미 보인다.** 차이는 시대 정보 품질 — lib은 사람이 정리, khs · 공개 경량본은 이름으로 자동 추정(khs 60개가 「전근대 공통(추정)」).
- 에이전트에게 **안 보이는 것은 `public/models` 사무 소품 12개뿐**이다(`/_sf_local` 밖). 출처 · 라이선스 기록이 없어 해랑 님 확인 후 입고한다.
- 자세한 구조 · 시대 고증 방식 · CDN 불러오기 원리 · khs 시대 보강 결과: **11절**.

## 5. 쿠키 · 주소 구조를 이렇게 정한 이유

- 해랑 님이 HttpOnly 쿠키 세션을 만들고 있다. 쿠키는 **화면과 API가 같은 사이트(같은 상위 도메인)**여야 브라우저가 막지 않는다. `*.vercel.app` 화면 + EC2 주소 조합은 제3자 쿠키로 막힌다.
- 그래서 `www.` `play.` `api.` `lobby.`를 **한 도메인 아래**에 둔다.
- 쿠키는 `Domain` 속성 없이 API 주소에만 붙는 쿠키(`__Host-` 접두어, `Secure` · `HttpOnly` · `SameSite=Lax`)로 만든다 🟡.
- 다른 방법(참고): 코드 주석에 「같은 주소의 `/api` 프록시가 기본」이라고 돼 있다. Vercel에서 `/api`를 EC2로 넘기면 쿠키 문제가 아예 없지만, ① 로비 웹소켓은 Vercel로 넘길 수 없고 ② 프록시 전송이 Vercel 무료 한도(Fast Origin Transfer 월 10GB)를 쓴다. 그래서 하위 주소 방식을 기본으로 한다 🟡.

## 9. 이용자가 늘었을 때 — 단계별

> 인원 수를 약속하지 않고 「무엇을 보면 언제 무엇을 바꾸는가」로 정한다. 단계별 한계 인원은 부하 시험 전까지 [미측정].

### 왜 늘릴 수 있는 구조인가
1. **3D는 플레이어 기기에서 그린다** → 1인당 서버 부담이 작다.
2. **무거운 파일은 CDN** → 몰림의 대부분을 앱 서버가 지지 않는다.
3. **로비는 10명짜리 방들의 모음** → 방끼리 독립이라 서버를 늘리면 나눠 담을 수 있다.
4. **진행 상태는 DB에 있다** → 확인 결과 NPC 멱등 저장소 · 승인 기록 · 힌트 잔액이 모두 DB 기반이고, 메모리 캐시는 읽기 전용 설정(일반 대사 팩)뿐이다. 그래서 API 서버를 여러 대로 늘려도 상태가 갈라지지 않는다 🟡(다중 서버 시험 전). 예외: 게시 콘텐츠 파일은 서버 디스크 폴더(`PUBLISHED_CONTENT_ROOT`)에서 읽으므로, 여러 대가 되면 모든 서버가 같은 파일을 받아야 한다.
5. **표준 기술만 쓴다**(MySQL · S3 호환 저장소 · Docker 없는 Python) → 다른 클라우드로 옮기기 쉽다.

### 단계표

> **동접 숫자는 예시일 뿐 전환 기준이 아니다.** 같은 동접이라도 요청 빈도 · 로비 메시지 · DB 작업에 따라 결과가 다르다. 전환은 운영 목표로 판단한다: 핵심 API p95 응답 · 오류율 / DB 연결 대기 · 잠금 · 느린 쿼리 / 로비 지연 · 재접속 실패율 / 배포 중 허용 중단 시간 / 장애 시 허용 데이터 손실(RPO) · 복구 시간(RTO). **DB 이중화(다중 AZ)는 동접과 무관하게, 유료 계약에서 긴 중단을 허용하지 않으면 먼저 필요하다.**

| 단계 | 상황 | 바꾸는 신호 | 바꾸는 것 | 조건 · 비고 |
|---|---|---|---|---|
| **S1 베타** | 약 100명 · 동접 30~50 | — | 지금 구성 그대로(EC2 1 + RDS micro + CDN) | 부하 시험으로 한계 측정 |
| **S2 홍보 · 축제 한 곳** | 동접 약 200 | EC2 CPU가 계속 높음 · 응답 300ms 초과 · RDS 연결 수 근접 | EC2 한 단계 키움(t4g.large 8GiB, 약 $60.7/월) · RDS 한 단계 키움 · 로비를 같은 서버 다른 프로세스로 여러 개 | 사양 변경은 **몇 분 중단** → 점검 시간 공지. 키운 서버로 다시 부하 시험 |
| **S3 여러 지역 동시 운영** | 동접 약 1,000 | 서버 한 대를 키워도 부족 · 배포 때 중단이 문제 | ⓪ 게시 콘텐츠 폴더(`PUBLISHED_CONTENT_ROOT`)를 모든 서버가 같은 내용으로 갖게(S3에서 받아 오기 또는 배포 이미지에 포함) ① API 서버 2대 이상 + 로드밸런서(ALB) ② 로비를 전용 서버로 분리 · Colyseus 공유 프레즌스(Redis) + 방 라우팅 ③ RDS 키우기 · 연결 수 관리(RDS Proxy 검토) ④ 배포를 서버 이미지(Docker 등)로 바꿈 ⑤ 다중 AZ로 DB 이중화 | Redis만 붙인다고 끝나지 않음(라우팅 필요). 비용 [가격 확인 필요] |
| **S4 동접 1만 이상** | 매출 단계 | — | 지역별 로비 묶음 · 매치메이커 · 이벤트 로그를 분석 저장소로 분리 · 읽기 복제본 · 자동 확장 그룹 | 비용은 방 수 · 서버 대수에 비례 |
| **급증(방송 · SNS)** | 짧은 시간 폭주 | 갑자기 동접 급증 | CDN이 에셋을 받아 냄 · 로비가 차면 혼자 모드 안내 · 요청 수 제한 · 필요하면 입장 대기열 | 첫 접속 1인 약 100~250MB(추정). CloudFront 무료 구간 넘으면 종량제 |

### 감시할 숫자(베타부터)

### 11.5 CDN에 빼 둔 에셋을 불러오는 원리 🟢

1. **배치 결과는 경로로 기록된다.** 08이 놓은 에셋은 manifest에 `/_sf_local/…/파일.glb`로 들어간다(`manifestPlace.mjs`가 이 아래 GLB만 허용, 파일 해시까지 확인).
2. **게임은 상수 하나를 기준으로 읽는다.** 나주맵 `publicAssetManifest.ts`의 `PUBLIC_ASSET_FOLDER = ${BASE_URL}_sf_local/` — manifest도, 거기 적힌 GLB도 이 폴더 기준.
3. **운영에서는 앞부분만 CDN으로.** `VITE_ASSET_BASE`(CDN 기본 주소) + 게시 데이터가 정한 케이스 버전 경로 + 같은 파일 경로 → `https://xxxx.cloudfront.net/c/<case_id>/v<버전>/_sf_local/…`.
4. **게시 때 manifest가 쓰는 파일만 같은 경로로 S3에 올린다.** 버전마다 폴더가 달라 진행 중인 세션은 자기 판 파일을 계속 읽고, 캐시도 꼬이지 않는다(12.1).
5. **제작은 원본, 플레이는 복사본.** 06 · 07 · 08은 맥의 로컬 파일을 읽으므로 CDN과 엮이지 않는다. 이미 CDN에 올라간 에셋도, 안 놓인 에셋도 똑같이 다시 고를 수 있다.

- 주의: 게임 코드에 `${BASE_URL}_sf_local/…`를 직접 만드는 곳(나주 퍼즐 3곳 등)이 있다 → 해랑 님이 `assetUrl()`로 바꿀 때 함께 바꾼다.

## 12. 장기 운영을 위한 연결 규칙 — 지금 정해 둘 네 가지 🟡

> 11/5 외부 검토 반영 · 저장소(`df55cfe`)로 확인한 사실 위에 세운 제안. EC2 한 대 · 수동 설치는 나중에 바꾸면 되지만, 아래 네 가지를 느슨하게 두면 재작업이 커진다.

### 12.1 콘텐츠 버전과 에셋 버전을 함께 고정하는 게시 방식

- **지금(확인):** 서버는 게시 버전마다 `client · server · npc · idmap` JSON을 fingerprint로 고정하고, 진행 중 세션은 그 묶음을 계속 쓴다(`content_release.md`). 그런데 **에셋 목록 · 파일 해시는 이 묶음에 없다.** 나주맵 manifest(`public/_sf_local/manifest.json`)는 화면 빌드에 들어 있어 모든 세션이 같은 것을 읽는다.
- **문제:** 플레이어 A가 v1을 진행 중일 때 v2를 게시하고 화면의 에셋 주소를 v2로 바꾸면, A가 v2 파일을 읽게 된다.
- **규칙:**
  1. 게시 단위 = 케이스 ID · 콘텐츠 버전 + (client · server · npc · idmap) + **에셋 목록과 파일 해시** + 그 버전의 CDN 경로 + 승인 기록 + 필요한 게임 실행부(화면 빌드) 버전.
  2. 기존 fingerprint는 그대로 두고 **에셋 목록 해시를 묶음에 추가**한다.
  3. 세션 생성 응답이 그 세션의 에셋 경로(`/c/<case_id>/v<버전>/`)를 내려 주고, 화면은 `VITE_ASSET_BASE` + 그 경로로 읽는다.
  4. 게시 순서: **파일 업로드 → 누락 · 해시 검사 → 서버 로딩 검사 → 신규 세션에 공개.** 실패하면 공개 보류, 이전 버전으로 되돌릴 수 있게.

### 12.2 「상호작용 정보가 있다」와 「실제로 할 수 있다」를 나눈다

- **지금(확인):** 에셋마다 역할 · 동작 · 숨길 자리 분류가 있고(`library-interaction.json`), 열린 판 · 찬 판 같은 상태 변형 파일 색인도 있다(`_sf_local/variants`). 하지만 「열기」가 적혀 있다고 그 GLB가 실제로 열리는 것은 아니다.
- **규칙:** 에셋 · 동작마다 네 칸을 둔다.

| 칸 | 예 |
|---|---|
| 기획상 가능한 행동 | 항아리를 열어 안의 단서 확인 |
| 준비된 표현 | 열린 상태 모델 / 뚜껑 분리 / 통째로 치우기 중 무엇이 있나 |
| 실행부 지원 | 어떤 공통 상호작용 컴포넌트로 도는가 |
| 검증 상태 | 실제 플레이에서 확인됐나 |

- 07 · 08 뒤에 **퍼즐이 요구하는 동작을 에셋 + 실행부가 지원하는지 코드로 검사**한다. 지원하지 않으면 대체 연출을 고르거나 생성 요청.

### 12.3 제작 공정 기록 형식 · 라이브러리 백업

- 제작은 지금처럼 맥에서 해도 된다. 다만 나중에 여러 지자체 요청을 받으려면 「요청 등록 → 작업 대기열 → 제작 작업자 → 단계별 결과 저장 → 사람 승인 · 반려 → 해당 단계 재실행 → 게시」가 필요하다.
- **지금 할 것은 형식뿐:** 모든 실행에 **작업 ID · 단계 · 입력 · 출력 버전 · 승인 상태 · 재실행 이력**을 남긴다. 그러면 로컬 제작기를 서버 작업자로 옮길 때 공정을 다시 설계하지 않는다.
- 라이브러리 비공개 원격 백업은 「팀 공유가 필요할 때」가 아니라 **베타 중 바로**(2.6).

### 12.4 인증 · 권한 — 여러 서버로 늘어날 조건까지

- **지금(확인):** `backend/app/main.py`의 CORS가 `allow_credentials=False`(로그인 쿠키를 아직 안 쓰므로). 쿠키 세션을 통합할 때 **함께 `True`로 바꾸고 출처를 정확히 지정**해야 한다 — `www` · `play` · `api`는 같은 상위 도메인이어도 서로 다른 출처다.
- 함께 넣을 것: 화면 요청에 자격 증명 포함 · 세션 만료 · 로그아웃 · 폐기 · 회원/게스트 플레이 소유권 · 상태 변경 요청의 CSRF 방어 · **서버가 여러 대여도 같은 결과가 나오는 세션 확인**(DB 또는 서명 토큰 — 서버 메모리 금지).
- 지자체가 직접 콘텐츠를 관리하는 단계: **기관별 콘텐츠 · 통계 · 승인 · 게시 권한 경계.** 지금 화면을 만들 필요는 없지만 계약 운영 전에는 설계.

### 12.5 표현 바로잡기

- 「서버 부담 0」 → **에셋 파일 전송에 따른 앱 서버 부담만 분리**한다. API · DB · 로비 부담은 남고, 플레이어 기기 성능 문제(첫 로딩 시간)도 별개다 — 초기 구역 우선 로딩 · 나머지 지연 로딩 · 텍스처 · 메시 경량화가 별도 과제.
- 첫 다운로드 100~250MB는 추정. 홍보 링크로 들어온 사람이 플레이를 시작하기까지 기다리는 시간을 측정한다(7절 5단계).
- Vercel 무료(Hobby)는 장기 사업 운영의 기본값이 아니다. 상업적 사용에 해당하는 시점에 요금제 · 호스팅을 바꾼다.
