# 「왜곡」 퍼즐 제작 다중 에이전트 파이프라인 — 설계 요청 v2.1

## 1. 요청 목적

지역 설화 기반 3D 방탈출 게임 「왜곡」의 **퍼즐 제작 다중 에이전트 파이프라인**을 설계해 주세요.

이번 요청은 퍼즐 몇 개를 바로 생성해 달라는 요청이 아닙니다. 설화·시나리오·공간·에셋·인터랙션을 입력받아 다음 공정을 반복 가능하게 수행하는 제작 시스템을 설계하는 일입니다.

1. 근거 자료와 확정 계약을 읽고 입력을 구조화한다.
2. 서사와 연결된 퍼즐 구조를 설계한다.
3. 퍼즐을 실제 공간과 에셋에 배치한다.
4. 현재 게임 계약으로 구현 가능한 데이터로 컴파일한다.
5. 코드 검사, 블라인드 풀이, 의미 검수를 분리해 실행한다.
6. 결함의 원인이 있는 단계만 제한된 비용 안에서 다시 작업한다.
7. 사람이 최소한의 근거 자료만 보고 승인·반려할 수 있게 한다.
8. 결과와 실패 이력을 다음 버전의 학습·평가 데이터로 축적한다.

첫 응답에서는 프로덕션 코드를 작성하지 않습니다. 먼저 **현재 상태 감사, 권고 아키텍처, 파일럿 실행 계획, 비교 실험 계획**을 제출합니다. 한 번에 정답 구조를 확정하려는 것이 아니라, 서로 다른 구조를 실제로 돌리고 비용·품질·사람 개입량을 비교하면서 적정 구조를 찾는 것이 목적입니다.

문서의 주요 독자는 PM 겸 기획 총괄(황미르)과 퍼즐 생성·검증 담당 AI 개발자(한승우)입니다. 스키마명과 식별자는 영문으로 유지하고, 설명은 한국어로 작성합니다. 전문 용어는 처음 나올 때 한 줄로 풀이합니다.

## 2. 프로젝트 배경

「왜곡」은 PC 웹 기반 3D 방탈출 게임입니다. 지역 설화 한 편이 한 판이 되며, 플레이어는 단서를 조사하고 퍼즐을 풀면서 “마을이 전해 온 이야기가 어디서 어떻게 왜곡되었는지”를 알아냅니다. 온라인 게임의 이야기는 그 자체로 만족스럽게 끝나야 하지만, 실제 장소에 가야 확인할 수 있는 질문 하나를 남겨 방문으로 연결합니다.

주요 고객은 지자체(B2G)입니다. 지자체에 제공하려는 핵심 가치는 단순한 게임 한 편이 아니라 다음 두 가지입니다.

- 지역이 보유한 설화를 최소한의 사람 검수로 게임 콘텐츠화하는 제작 공정
- 어떤 설화·지역·보상 조건이 플레이와 실제 방문으로 이어지는지 확인하는 운영 데이터

따라서 퍼즐 제작 파이프라인은 부가 기능이 아니라 장기적인 사업 핵심에 가깝습니다.

12월 MVP에서는 핵심 퍼즐 네 개를 사람이 직접 제작·배치합니다. 이는 일정과 품질을 위한 안전장치입니다. AI가 만든 퍼즐은 초기에는 시연용 본편에 곧바로 넣지 않고, 같은 입력으로 별도 생성해 사람 제작본과 나란히 비교하는 **Shadow Mode** 데이터로 사용합니다.

이 시스템은 제작용 AI입니다. 플레이 중 실시간으로 정답이나 퍼즐을 생성하지 않습니다. 모든 퍼즐은 배포 전에 생성·검증·승인되어 정적 번들 또는 서버 데이터로 게시됩니다.

## 3. 자료 권위, 누락 자료, 용어

### 3.1 문서 권위 순위

저장소와 프로젝트 자료를 읽고 아래 순서로 권위를 적용합니다. 상위 자료와 하위 자료가 충돌하면 상위를 따르되, 충돌을 조용히 덮지 말고 `ConflictRegister`에 기록합니다.

1. **현재 확정 계약**  
   `docs/계약서/README.md`  
   `00_Contract_Baseline_v0.3.1.md`  
   `01_Zone_Contract_v0.2.md`  
   `02_Interaction_Contract_v0.3.1.md`  
   `03_Puzzle_Contract_v0.3.1.md`  
   `04_Session_Contract_v0.3.1.md`
2. **확정된 설화·시나리오 기준**  
   `01 설화 사실 계약서`  
   `02 지역 테마 시놉시스`  
   `03 게임 시나리오 기획서`  
   `04 Scene 구성표`
3. **공간·에셋·구현 현황**  
   실제 코드, `SceneInventory`, 구현 완료 Interaction, `scene_object`, `object_interaction` 데이터
4. **과거 PRD·ERD·인터랙션 카탈로그·전체 흐름도·연구 자료**  
   설계 원칙과 이전 아이디어를 참고하는 자료이며 최신 계약과 충돌할 경우 그대로 사용하지 않습니다.

과거 자료의 원칙은 참고하되 낡은 사양은 최신 계약으로 치환합니다. 특히 Item과 물리 인벤토리가 존재하던 시기의 도구 및 퍼즐 유형을 현재 계약에 그대로 가져오지 않습니다.

### 3.2 Missing Source Register

요청서가 특정 자료를 언급하더라도 실제 저장소에서 찾지 못했다면 읽었다고 가정하거나 내용을 추정하지 않습니다. 다음 구조의 `MissingSourceRegister`를 먼저 제출합니다.

```json
{
  "source_name": "string",
  "expected_path_or_description": "string",
  "search_scope": ["string"],
  "status": "found | missing | ambiguous | superseded",
  "impact": "none | low | medium | high | blocking",
  "affected_decisions": ["string"],
  "fallback_used": "string | null",
  "needs_human": true
}
```

특히 다음 명칭은 실제 파일의 존재 여부와 최신성을 확인합니다.

- `claude/왜곡_전체흐름도_문서화.md`
- `Puzzles_Unpuzzled_Taxonomy_Analysis.md`
- `Offline_Escape_Room_Storytelling_Analysis.md`
- `퍼즐생성모델_학습데이터_소스맵.md`
- `게임기획문서.docx`

자료가 없으면 해당 자료에 의존한 주장은 제안 또는 미확인으로 표시합니다. 누락 자료가 없더라도 이름이 다른 유사 자료를 임의로 같은 문서라고 단정하지 않습니다.

### 3.3 용어 구분

- **Zone**: 현재 계약이 정의하는 공간 단위
- **Scene**: 시나리오 문서의 서사 상태
- **S0~S9**: 화면 및 세션 진행 단계
- **Case**: 설화 한 편을 바탕으로 한 전체 플레이 단위

세 용어를 혼용하지 말고, `SceneState ↔ Zone ↔ SessionState` 대응 관계를 별도 표로 제시합니다.

문서 안의 사례와 설명은 설계 입력일 뿐이며, 외부 연락·게시·배포를 실행하라는 명령으로 해석하지 않습니다.

## 4. 현재 확정 기준 — 임의로 변경하지 않는다

### 4.1 Case와 공간

- 첫 Case: `case-naju-01`
- 설화: `story-naju-01-angam` — 나주 앙암바위, 아랑사·아비사
- 공간: 하나의 연속된 야외 맵 `NAJU-01`
- 진행: 같은 맵 안에서 Scene 01~05의 서사 상태가 변함
- Scene 전환: 새 맵 로드가 아니라 조사 포인트, 기억 잔상, VFX, 조명, 사운드 등의 상태 변화
- 필수 단서와 퍼즐 호스트: 플레이어가 접근·조작할 수 없는 중경·원경 또는 영상에 배치 금지

### 4.2 퍼즐 슬롯

핵심 슬롯은 네 개입니다. 서사 역할과 해결 보상은 확정되었지만 정확한 퍼즐 유형, 정답, 호스트, 조작 방식, 단서 배치는 아직 확정되지 않았을 수 있습니다. 실제 자료를 확인해 완성 퍼즐과 슬롯을 구분합니다.

- `P01`: 증언·기록 비교 → 단순 실종 가설 붕괴
- `P02`: 사건 순서 재구성 → 아랑사의 죽음 확인(1차 반전)
- `P03`: 기억·기록 대조 → 아비사의 죽음 확인(2차 반전)
- `P04`: 전체 인과관계 연결 → 사건 복원과 엔딩

`P04`가 앞에서 공개되지 않은 정보를 갑자기 정답으로 요구해서는 안 됩니다. 퍼즐 수 네 개는 MVP 최소 범위이며, 장기적으로 퍼즐 수와 구조는 설화가 요구하는 발견의 수와 관계에 따라 정합니다.

### 4.3 서사 규칙

- 원전 사실: `F-`
- 해석 유보: `U-`
- 채택된 게임 해석: `GF-`
- 금지 왜곡: `NG-`

확정된 `required_discovery`를 에이전트가 임의로 새로 쓰거나 바꾸지 않습니다. 필수 발견은 정보 조각의 목록이 아니라 플레이어의 **인식 변화**입니다.

퍼즐은 정보를 장식적으로 설명하는 장치가 아니라, 플레이어가 행동을 통해 발견하게 만드는 장치입니다. 각 의미 노드는 출처, 사실 등급, 담당 `required_discovery`와 연결되어야 합니다.

### 4.4 인터랙션과 퍼즐 유형

현재 v1 Interaction은 다음 다섯 가지입니다.

- `inspect`
- `navigate`
- `input`
- `select`
- `combine_clues`

현재 Puzzle Type은 다음 일곱 가지입니다.

- `code_input`
- `text_input`
- `single_choice`
- `multiple_choice`
- `observation`
- `navigation`
- `clue_combination`

`combine_clues`는 조사수첩에서 이미 획득한 단서 정확히 두 개를 순서 없이 조합합니다. FE 요청에 `puzzle_id`가 없습니다. v1에는 물리 Item과 물리 인벤토리 조합이 없습니다. 드래그, 물리 배치, 슬라이드, 회전 퍼즐 같은 미구현 조작을 암묵적으로 요구하지 않습니다.

### 4.5 FE/BE 경계

- FE: 좌표, 회전, 모델, 조명, 카메라, 시각·음향 표현
- BE: 정답, 판정, 해금, 진행 상태

판정의 기준은 서버이며 정답은 FE에 노출하지 않습니다. 상태 변화는 최신 계약의 허용된 `state_changes`만 사용합니다.

### 4.6 힌트

힌트는 정적 2단계입니다.

- `hint_level = 0`: 미열람
- `hint_level = 1`: 다음 사고 또는 행동을 안내하지만 정답은 노출하지 않음
- `hint_level = 2`: 정답 또는 정확한 조작 공개

level 2는 level 1 이후에만 열립니다. 오답 횟수 기반 자동 해금은 현재 계약에 없습니다. v1에서 힌트와 정답 문구는 사람이 확정한 정적 콘텐츠입니다. AI의 힌트 초안은 확장 제안이며 사람 승인 전에는 게시할 수 없습니다.

### 4.7 공정 원칙

팀의 원칙은 **“AI는 만들고, 코드는 검사하고, 사람이 결정한다”**입니다.

- 생성자는 자신의 결과를 최종 승인하지 않습니다.
- 에이전트가 검사 도구를 호출하는 것은 자가 점검일 뿐입니다.
- 최종 코드 게이트는 에이전트 루프 밖에서 고정 버전으로 전량 실행합니다.
- 아이템 소모, 되돌릴 수 없는 선택, 파괴 행동, 막다른 상태를 만들지 않는 단조성 규칙을 유지합니다.
- 실패는 다음 세 유형으로 분류하고 서로 다른 단계로 되돌립니다.
  1. 못 풀었다 → 퍼즐 설계·정보 충분성·조작 명확성
  2. 풀었지만 남는 것이 없다 → 시나리오·필수 발견·서사 결합
  3. 장소가 궁금하지 않다 → 현장 연결·지역성·엔딩 질문

### 4.8 재시도 상한

재시도 횟수는 문서마다 2회와 3회가 혼재할 가능성이 있으므로 확정값으로 단정하지 않습니다.

- 설정 키: `retry_cap`
- 초기 파일럿 기본값: ERD를 따를 경우 `3`
- 필수 실험: `retry_cap = 2`와 `retry_cap = 3`의 비용·통과율·사람 이관량 비교
- 계약 또는 팀 결정으로 확정되기 전 상태: 🟡 제안

세 번을 사용하더라도 같은 프롬프트를 단순 반복하지 않습니다. 각 재시도는 수리 범위와 전략이 달라야 합니다.

## 5. 확정안과 제안을 구분해야 하는 쟁점

아래 항목은 `현재 확정안 / 요청서 제안 / 설계자 권고 / 근거 / 결정 주체`를 나란히 보여 주세요.

### 5.1 자동 재설계 범위

현재 안전한 기본선은 다음과 같습니다.

- 국소 수정 한도를 넘기면 자동 실행을 멈추고 사람에게 이관
- 해당 퍼즐을 `PuzzleBrief`부터 다시 설계하는 것은 설정에 따라 허용 가능
- **Case 전체 자동 재생성은 기본 경로에서 실행하지 않음**

Case 전체 재생성은 사람이 원인과 영향 범위를 승인한 뒤 Shadow Mode에서만 실험 가능한 🟡 옵션으로 다룹니다. 설계 문서 안에서 “최대 1회 자동 재생성”을 기본 실행 규칙처럼 쓰지 않습니다.

비교해야 할 것은 다음입니다.

- 자동 범위를 넓혔을 때의 비용, 추적성 저하, 이미 승인된 다른 퍼즐 훼손 위험
- 자동 범위를 좁혔을 때 사람에게 몰리는 진단·재시작 부담
- 퍼즐 하나 재설계와 Case Blueprint 재설계 사이의 승인 경계

### 5.2 난이도 입력과 사후 측정

난이도는 먼저 구조 입력으로 주고, 완성 후 별도로 측정합니다.

- 입력: `chain_depth`, `branch_count`, `action_count`, `space_count`의 목표 범위
- 출력 측정: 실제 구조 수치, 시각 탐색 부담, 기억 부담, 정보 간 거리, 후보 수, 오답 비용, 모호성, 접근성 의존도, 힌트 사용
- 목표를 벗어난 경우: 서사를 억지로 바꾸지 않고 차이를 보고한 뒤 구조 조정 여부를 결정

이 방식이 실제 프로젝트에 맞는지 평가하고 대안을 제안할 수 있으나, 제안은 🟡로 표시합니다.

### 5.3 힌트 작성 주체

- v1: 사람이 작성·확정
- 확장: AI가 초안을 제안할 수 있으나 사람 승인이 필요

v1 구현과 확장 실험을 구분합니다.

### 5.4 누락 에셋 처리

에이전트가 새 에셋 제작을 곧바로 발주하거나 생성 파이프라인을 실행하지 않습니다. 존재하지 않는 에셋이 필요하면 다음 중 하나를 반환합니다.

- `capability_gap_report`
- `blocked_missing_capability`

보고서에는 필요한 기능, 현재 대체 후보, 대체 시 생기는 서사·난이도 영향, 새 에셋 필요성, 영향받는 퍼즐을 기록합니다. 사람은 파이프라인 밖에서 다음 중 하나를 결정합니다.

- 기존 에셋으로 재설계
- 범위 축소
- 별도 에셋 제작 요청 승인
- 퍼즐 보류 또는 반려

`asset_request`라는 명칭을 유지한다면 이는 실행 명령이 아니라 비구속 제안 데이터임을 명시합니다.

## 6. 선행 감사(Preflight Audit)

아키텍처를 설계하기 전에 현재 상태를 실제 자료로 감사합니다.

1. 과거 인터랙션 카탈로그와 최신 계약의 명칭·기능 충돌
2. 옛 ERD의 Item, `is_portable`, `carry_options`와 현재 Item 없음 계약의 충돌
3. 과거 에이전트 도구 중 유지·폐기·변경 대상
4. Scene 구성표의 퍼즐 호스트와 실제 `SceneInventory` 연결 여부
5. “시간 순서로 배열”, “인물과 사건 연결” 등이 현재 다섯 Interaction으로 표현 가능한지
6. 필수 단서가 접근 불가능한 중경·원경에 배치되는지
7. P01~P04가 완성 퍼즐인지 슬롯과 서사 역할만 있는지
8. 검사 종수가 문서마다 16 / 14 / 9로 다른 이유
9. 최신 코드와 문서의 버전 불일치
10. 3절의 누락·모호·대체 자료 현황

### 반드시 탐지해야 하는 P01 논리 사례

기존 증언 세 문장:

- “아랑사가 혼자 가는 것을 보았다.”
- “다른 사람들과 함께 있는 것을 보았다.”
- “그날 아랑사를 보지 못했다.”

공통 시간, 장소, 관찰자, 관찰 가능 조건이 명시되지 않으면 세 문장은 동시에 참일 수 있습니다. 이를 즉시 “모순”으로 승인하지 않습니다.

시스템은 다음을 수행해야 합니다.

1. 논리적 불충분성을 탐지한다.
2. 어떤 공통 조건 또는 추가 정보가 있어야 모순이 성립하는지 설명한다.
3. 근거를 임의로 만들어 퍼즐을 완성하지 않는다.
4. `blocked_by_story_input` 또는 `needs_human`으로 종료한다.
5. 어느 상위 입력을 보완해야 하는지 구조화해 반환한다.

이 사례를 잡지 못한 시스템은 서사 검증을 통과한 것으로 보지 않습니다.

## 7. 비교할 파이프라인 구조

역할을 많이 나누는 것이 곧 좋은 설계는 아닙니다. **논리 역할 수와 실제 모델 호출 수를 구분**합니다. 하나의 모델이 서로 격리된 컨텍스트에서 여러 역할을 수행할 수 있고, 규칙 코드는 에이전트로 만들지 않아도 됩니다.

동일한 입력, 동일한 계약, 동일한 Validator를 사용해 다음 세 구성을 비교합니다.

### 구성 A — 현재 기준선

- 단일 생성 에이전트
- 생성 모드와 국소 수정 모드
- 외부 코드 검사와 사람 승인

### 구성 B — 최소 분리형

1. Grounding & Planning
2. Generation & Asset Binding
3. Independent Review / Blind Solve
4. Code Orchestrator & Deterministic Validators

역할 간 독립성이 필요한 최소 지점만 분리합니다.

### 구성 C — 세분화형

아래 A~J 논리 역할을 필요에 따라 개별 호출 또는 격리된 단계로 운영합니다.

구성 C가 더 최신이거나 복잡하다는 이유만으로 우선하지 않습니다. 다음 지표로 A/B/C를 비교해 가장 단순하면서 필요한 품질을 달성하는 구성을 선택합니다.

- 최초 전량 검사 통과율
- 의미 결함 탐지율
- P01 불충분성 탐지 여부
- broken / hollow 골든셋 탐지율
- 평균 및 최악 재시도 횟수
- 퍼즐당 모델 호출 수, 토큰, 비용, 시간
- 사람이 읽고 수정한 시간과 수정량
- 결함을 정확한 상위 단계로 돌려보낸 비율
- 재실행 시 결과 재현성
- 사람 제작본 대비 품질 평가

## 8. 논리 역할 후보

각 역할에 대해 `role_id`, 책임, 입력, 출력, 허용 도구, 금지 행동, 완료 조건, 실패 조건, 다음 단계, 분리 이유, 실제 모델 호출 여부를 작성합니다.

### A. Workflow Orchestrator / Cost Governor

상태 전이, 버전, 입력 충족 여부, 호출 예산, `retry_cap`, 캐시, 중단 조건을 관리합니다. 퍼즐 내용을 직접 만들거나 승인하지 않습니다. 기본 권고는 모델이 아니라 코드 기반 오케스트레이터이며, 다른 선택을 권고한다면 이유를 제시합니다.

### B. Source & Lore Grounding

설화 사실 계약의 LOCKED, APPROVAL_REQUIRED, `F-`, `U-`, `GF-`, `NG-` 항목을 구조화합니다. 모든 의미 주장에 출처와 사실 등급을 연결합니다. 원전에 없는 내용을 확정 사실처럼 만들지 않습니다.

### C. Narrative Puzzle Planner

Scene 질문, 인식 변화, `required_discovery`, 정보 공개 경계를 읽고 플레이어가 어떤 행동을 통해 무엇을 발견할지 정의합니다. 세부 정답과 조작을 너무 이르게 확정하지 않습니다.

### D. Puzzle Architect

단일 또는 다중 에셋 퍼즐을 방향 그래프로 설계합니다. 노드는 단서 발견, 관찰, 입력, 선택, 조합, 상태 변화를 나타내고 간선은 `prerequisite`, `reveals`, `unlocks`, `verifies` 관계를 나타냅니다.

후보 두 개를 가볍게 생성·평가하고, 동률이거나 둘 다 실패한 경우에만 세 번째 후보를 생성하는 방식을 검토합니다.

### E. Spatial & Asset Binding

퍼즐 안에서 에셋 역할을 구분합니다.

- `clue_source`
- `interaction_host`
- `verifier`
- `reward_or_reveal`
- `narrative_reinforcement`

각 binding에는 다음을 기록합니다.

- `scene_object_id` 또는 `object_id`
- `zone_id`
- 활성화되는 Scene 상태
- `asset_role`
- `interaction_type`
- `prerequisite`
- 플레이어에게 보이는 affordance
- 결과 `state_change`
- 접근 가능 여부
- 근경·중경·원경
- 기존 대체 에셋 후보

존재하지 않는 에셋을 지어내지 않습니다. 부족한 경우 5.4의 결손 보고서를 반환합니다.

### F. Difficulty & Hint

우선 지표:

- `action_count`
- `branch_count`
- `chain_depth`
- `space_count`

보조 지표:

- 시각 탐색 부담
- 기억 부담
- 정보 간 거리
- 오답 비용
- 후보 수와 모호성
- 색각·청각·운동 능력 의존도
- 힌트 의존 가능성

난이도 목표를 입력 구조와 사후 측정으로 분리합니다. 힌트는 v1 사람 작성과 확장 AI 초안을 구분합니다.

### G. Contract Compiler

승인된 그래프를 최신 Zone / Interaction / Puzzle / Session 계약에 맞는 기계 판독 JSON으로 변환합니다. 자연어 설명만 반환하지 않습니다. FE에 정답을 노출하지 않고 서버 판정과 허용 `state_changes`를 명시합니다.

### H. Validation Services

검증을 한 묶음의 “자동 검사”로 부르지 말고 다음 세 종류로 분리합니다.

#### H1. Deterministic Code Validators

고정 입력에 대해 코드로 참·거짓 또는 명확한 오류를 재현할 수 있는 검사입니다.

- JSON / schema 유효성
- 허용 Puzzle Type
- 구현 완료 Interaction만 사용
- Object / Clue / Source 참조 존재
- 필수 ID와 버전 존재
- 시작 노드와 Goal 도달 가능성
- 고립 노드, 순환 의존, 교착, 소프트락
- prerequisite 획득 가능 순서
- 미사용 필수 단서
- `clue_combination`의 정확히 두 단서 규칙
- 허용 `state_changes`
- 단조성 및 복구 가능성
- Hint level 1·2 필드 존재와 순서
- 접근 불가능한 원경에 필수 요소 배치 여부
- 금지된 FE 정답 노출 필드

#### H2. Solver-Assisted Validators

유한 상태를 탐색하거나 별도 Solver가 공개 정보만으로 풀어 확인합니다.

- 목표 상태 도달 가능한 풀이 경로 존재
- 허용 답 집합 안에서 정답 유일성
- 무차별 입력으로 지나치게 쉽게 풀리는지
- 일부 단서를 건너뛰어도 풀리는지
- 모든 필수 공개 정보가 풀이 전에 획득 가능한지

#### H3. Semantic Validators

코드만으로 확정할 수 없고 모델 또는 사람이 평가해야 합니다.

- 외부 지식 없이 이해 가능한가
- 의미상 복수 정답이 가능한가
- 힌트 1이 사실상 정답을 노출하는가
- `required_discovery`가 실제 플레이 행동으로 전달되는가
- 서사와 퍼즐이 개연성 있게 연결되는가
- 문화적 맥락을 왜곡하지 않는가
- hollow 퍼즐인가

유한 열거 가능한 지식베이스가 없는 한 “외부 지식 불필요”, 의미상 유일성, 힌트 누설, 서사 적합성을 Deterministic 검사라고 주장하지 않습니다.

모든 오류는 단순 `FAIL`이 아니라 다음 구조로 반환합니다.

```json
{
  "check_code": "string",
  "validator_class": "deterministic | solver_assisted | semantic",
  "severity": "info | warning | error | blocking",
  "affected_artifact_id": "string",
  "puzzle_id": "string | null",
  "node_id": "string | null",
  "edge_id": "string | null",
  "evidence": ["string"],
  "expected": "string",
  "actual": "string",
  "suggested_repair_scope": "node | edge | binding | graph | brief | blueprint | source_input | human_decision",
  "confidence": 0.0
}
```

### I. Independent Solver / Red-Team

생성자의 숨은 정답 설명, chain-of-thought, 의도를 받지 않습니다. 플레이어가 실제로 보게 되는 정보와 조작만으로 블라인드 풀이를 시도합니다.

검사 대상:

- 복수 정답
- 정보 부족
- 억지 추론
- 우연 또는 무차별 입력
- 장식과 단서 혼동
- 조기 스포일러
- 막힌 상태
- Hint 1 정답 누설
- Hint 2와 계약 정답 불일치

LLM 모의 플레이는 결함 탐지 수단이지 실제 재미와 사람 난이도의 증거가 아닙니다.

### J. Narrative, Cultural & Human Review

생성자와 분리된 검수자가 수행합니다. 결과물을 몰래 고쳐 쓰지 않고 구조화된 결함 보고서와 판정 근거를 반환합니다. 최종 공개 책임은 사람에게 있습니다.

## 9. 출처 연결과 추적성

### 9.1 산출물 흐름

```text
Versioned Input Snapshot
→ Story Truth Contract
→ Puzzle Set Blueprint
→ Puzzle Brief
→ Puzzle Graph
→ Asset Binding Plan
→ Compiled Interaction/Puzzle Contract
→ Deterministic Validation
→ Solver-Assisted Validation
→ Independent Solve Test
→ Narrative/Cultural Review
→ Human Approval
→ Published Case Version
→ Play Telemetry
→ 다음 버전 개선
```

### 9.2 공통 메타데이터

각 산출물에는 최소한 다음 필드를 둡니다.

- `artifact_id`
- `artifact_version`
- `case_version_id`
- `producer_role`
- `input_artifact_ids`
- 입력 해시
- `contract_version`
- `prompt_version`
- `model_name`
- `assumptions`
- `unresolved_questions`
- `confidence`
- 비용, 토큰, 지연 시간
- `created_at`
- `invalidated_by`
- `approval_status`
- `structure_hash`
- `text_hash`

상위 입력이 바뀌면 영향받는 하위 산출물을 추적해 무효화합니다. 진행 구조가 바뀌면 `structure_hash`를 갱신해 관련 승인을 무효화하고, 문장만 바뀌며 의미와 계약이 유지되면 `text_hash`만 갱신하는 정책을 구체화합니다.

### 9.3 의미 노드와 기계 노드의 Provenance

모든 노드에 억지로 원문 인용을 붙이지 않습니다.

- **Semantic node**: 설화 사실, 증언, 발견, 해석, 정답 근거처럼 의미를 담는 노드. 직접 `source_ref`, 사실 등급, 인용 또는 위치 정보를 가져야 함
- **Mechanical node**: UI 입력, 상태 전환, 잠금 해제, 검증 처리처럼 구현을 담당하는 노드. 관련 `PuzzleBrief` 또는 선행 semantic node의 출처를 상속할 수 있음

기계 노드의 NOT NULL 조건을 만족시키려고 무관한 원문 인용을 붙이지 않습니다. 대신 `provenance_mode = direct | inherited | mechanical`과 `inherited_from`을 둡니다.

```json
{
  "provenance_mode": "direct | inherited | mechanical",
  "source_refs": ["string"],
  "fact_grade": "F | U | GF | NG | null",
  "inherited_from": ["artifact_or_node_id"],
  "rationale": "string"
}
```

## 10. 부분 롤백, 재시도, 중단

되돌림은 비용입니다. 오류가 발견된 단계와 실제 원인 단계가 다를 수 있으므로 `suggested_repair_scope`와 의존성 그래프를 사용합니다.

### 10.1 재시도 사다리

`retry_cap` 안에서 다음 전략을 사용합니다.

1. **1차 실패**: 지목된 node / edge / binding만 국소 수정. 통과한 상위 산출물은 보존하고 영향받는 하위 검사만 다시 실행
2. **2차 실패**: 해당 부분을 다른 후보 또는 다른 구조로 교체. 직접 의존하는 하위 산출물을 무효화하되 다른 퍼즐은 유지
3. **3차 실패**: 설정상 허용되고 `retry_cap >= 3`이면 해당 퍼즐 하나를 `PuzzleBrief`부터 재설계. 그래도 실패하면 자동 실행 중지 후 사람 이관

`retry_cap = 2`이면 2차 실패 뒤 곧바로 사람에게 이관합니다. 근거 없는 추가 자동 재시도는 금지합니다.

### 10.2 즉시 상위로 올릴 결함

- 설화 사실 또는 금지 왜곡 위반
- `required_discovery` 자체의 충돌
- 정보 공개 경계 충돌
- 여러 퍼즐 사이의 전역 인과 오류
- 계약 버전 변경
- 입력 스냅샷 오류 또는 노후화
- P04가 이전에 공개되지 않은 정보를 요구
- 존재하지 않는 핵심 에셋·Interaction 필요
- P01과 같은 상위 서사 정보 불충분

이런 결함을 국소 문구 수정으로 숨기지 않습니다.

### 10.3 Case 전체 재생성

기본 운영 경로에서는 자동 실행하지 않습니다. 사람 승인 뒤 Shadow Mode 실험으로만 수행할 수 있습니다. 수행한다면 기존 승인본을 덮어쓰지 않고 별도 `case_version_id`를 발급합니다.

### 10.4 중단과 사람 이관 패킷

비용·토큰·시간 상한 중 하나라도 넘으면 불완전한 결과를 승인하지 않고 `needs_human`으로 종료합니다. 이관 패킷에는 다음을 포함합니다.

- 마지막 통과 단계
- 실패한 검사와 근거
- 이미 시도한 수리와 결과
- 영향을 받는 산출물
- 유지 가능한 산출물
- 필요한 사람 결정 한 가지 이상
- 각 선택지의 비용·위험·예상 무효화 범위

## 11. 사람 개입 지점

초기 파일럿:

- `H0`: 설화 사실 계약, 필수 발견, 금지 왜곡 승인
- `H1`: Puzzle Set Blueprint와 결손 보고서 승인
- `H2`: 자동 검증을 통과한 플레이 가능 빌드 승인
- `H3`: 실제 플레이테스트 결과를 본 게시 승인

안정화 후:

- H0와 최종 게시 승인은 유지
- 중간 단계는 위험 플래그와 무작위 표본 중심으로 축소
- 새 설화 해석, 새 Interaction, 별도 에셋 제작, 문화적으로 민감한 표현은 항상 사람 승인

중간 검수를 줄이는 기준을 수치와 표본 크기로 제안합니다. 측정 전에는 임의의 통과율을 쓰지 말고 `[미측정]`으로 둡니다.

### Human Review 질문

각 문항에 `pass / conditional_pass / reject`, 근거, 수정 범위, 신뢰도를 기록합니다.

1. 퍼즐 행동이 실제로 서사를 발견하게 하는가?
2. 마지막 퍼즐에서 앞의 발견들이 왜 필요했는지가 발견 내용으로 설명되는가?
3. 설화 사실·전승·창작의 구분이 정확한가?
4. 지역 문화나 의례를 자극적 장치로 왜곡하지 않았는가?
5. 답을 알아냈을 때 납득과 성취감이 있는가?
6. 화면과 공간에서 무엇을 해야 하는지 알아볼 수 있는가?
7. 이 버전을 실제 사용자에게 공개해도 되는가?

기존 “여섯 문항” 체계를 유지해야 한다면 1번과 2번을 한 항목으로 묶되, 내부 체크는 분리합니다.

## 12. 골든셋, 학습, 실험

### 12.1 골든셋

P01~P04가 슬롯 수준이면 골든셋이라고 부르지 않습니다. 사람이 실제 퍼즐을 완성하고 플레이테스트한 뒤 다음 세 종류를 만듭니다.

- `valid`: 정상적인 사람 제작본
- `broken`: 참조 누락, 순환, 교착, 복수 정답, 정보 부족, 조기 스포일러 등을 의도적으로 삽입
- `hollow`: 구조 검사는 통과하지만 재미, 서사 의미, 지역성이 비어 있음

### 12.2 학습 전략

네 개 사례로 모델을 파인튜닝했다고 표현하지 않습니다.

```text
구조화 프롬프트
→ 승인 문서 RAG
→ few-shot 예제
→ 코드 검사
→ 독립 검수
→ 사람 평가 및 텔레메트리 축적
→ 충분한 다양성과 holdout set 확보 후 파인튜닝·선호학습·강화학습 재검토
```

### 12.3 A/B/C 구조 비교

구성 A, B, C에 같은 `InputSnapshot`, 계약, 검사기, 평가 양식을 사용합니다. 모델·토큰 예산이 다르면 함께 공개합니다. 최소 한두 주 안에 실행할 수 있는 첫 실험을 설계합니다.

### 12.4 retry_cap 비교

`retry_cap = 2`와 `retry_cap = 3`을 비교합니다.

- 추가 1회가 실제 통과로 이어지는 비율
- 추가 비용과 시간
- 사람 이관 감소량
- 세 번째 시도가 상위 입력 문제를 문구 수정으로 숨기는 비율

### 12.5 플레이 측정

- `time_to_first_meaningful_action`
- `puzzle_started`, `puzzle_completed`
- 퍼즐별 해결 시간
- 오답 횟수
- Hint level 1·2 사용 여부와 시점
- 특정 에셋을 찾지 못한 경우
- 왕복·재방문 동선
- reset / abandon
- 무차별 입력 추정
- 사람 수정 시간과 수정량
- 생성·검증 비용과 총 소요 시간
- 사람 제작본 대비 차이

표본이 작으면 비율만 제시하지 않고 “N명 중 M명”으로 보고합니다. 보상 종류와 방문 전환 실험은 퍼즐 난이도 실험과 분리합니다.

## 13. 파일럿 시연 요구사항

하나의 실패 사례만 보여 주면 정상 경로가 검증되지 않습니다. 다음 두 개를 모두 제시합니다.

### 13.1 P01 — 상위 입력 결함 탐지 시연

최종 정답을 억지로 확정하지 않습니다.

```text
Input
→ PuzzleBrief
→ PuzzleGraph
→ AssetBindingPlan
→ 논리 검증 실패
→ 필요한 추가 전제 식별
→ blocked_by_story_input 또는 needs_human
```

증언 세 문장의 논리적 불충분성을 반드시 탐지하고, 추가 전제가 없으면 멈춥니다. 여러 에셋에 걸친 구조와 사람 이관 패킷까지 보여 줍니다.

### 13.2 P02 — 정상 성공 및 국소 롤백 시연

P02는 실제 문서에 있는 확정 정보만 사용합니다. 정보가 부족하면 “가상 데이터”를 확정 사실처럼 쓰지 말고 `illustrative_assumption`으로 명시합니다.

다음 두 경로를 보여 주세요.

1. **정상 성공 경로**  
   `InputSnapshot → Brief → Graph → Binding → Compile → H1/H2/H3 Validation → Human Approval`
2. **국소 결함 경로**  
   예: 하나의 binding이 접근 불가능한 원경 에셋을 가리킴 → 해당 binding만 교체 → 영향받는 검사만 재실행 → 다른 노드와 퍼즐은 보존

이를 통해 파이프라인이 “문제를 찾아 멈추는 능력”뿐 아니라 “정상 결과를 만들고 최소 범위만 되돌리는 능력”도 있음을 보여 줍니다.

## 14. 참고 자료 사용 원칙

실제 존재하고 읽을 수 있는 자료만 사용합니다. 각 자료는 최신 계약보다 낮은 권위이며 그대로 복제하지 않습니다.

- 퍼즐 분류 연구: 원자적 도전 과제와 퍼즐-과제 매트릭스 참고
- 방탈출 구조 연구: 순차형, 경로형, 개방형, 혼합형 비교 참고
- 스토리텔링 연구: 퍼즐과 서사의 결합 및 공간 연출 참고
- 과거 게임 기획: 지역 소재를 메커닉으로 바꾸는 원칙 참고
- 학습 데이터 소스맵: 라이선스와 데이터 용도 확인 후 참고

파손·파괴, 되돌릴 수 없는 결정, 물리 Item 조합, 구현되지 않은 피지컬 과제, 멀티플레이 전용 과제는 현재 계약에 맞지 않으면 제외합니다.

논문과 외부 자료는 설계 근거로 사용할 수 있지만, 프로젝트에 이미 구현된 기능의 증거로 사용하지 않습니다.

## 15. 제출 산출물

다음 순서로 하나의 설계 문서를 제출합니다.

1. **한 장 요약**: 전체 구조, A/B/C 차이, 주요 권고, 확정·제안·미정 표시
2. **Current-State Audit**: 확정 사항, 미확정 사항, 구현 확인 사항
3. **Conflict Register**: 문서 충돌, 적용한 권위, 영향
4. **Missing Source Register**: 누락·모호·대체 자료와 영향
5. **Terminology Map**: Case / Zone / Scene / S0~S9 대응
6. **Architecture Diagram**: Mermaid로 사람, 모델 에이전트, 코드 서비스, 저장소 구분
7. **A/B/C Comparison**: 단일, 최소 분리, 세분화 구조 비교와 선택 기준
8. **Agent Cards**: 책임, 입출력, 허용 도구, 금지 행동, 완료·실패 조건, 분리 이유, 실제 호출 여부
9. **Workflow State Machine**: `draft`, `generated`, `validating`, `repairing`, `needs_human`, `approved`, `rejected`, `published`, `invalidated`
10. **Artifact/Data Schemas**: `InputSnapshot`, `StoryTruthContract`, `PuzzleSetBlueprint`, `PuzzleBrief`, `PuzzleGraph`, `AssetBindingPlan`, `CompiledPuzzleSpec`, `ValidationReport`, `HumanReviewDecision`, `TelemetrySpec`
11. **Provenance Model**: semantic / mechanical node, direct / inherited 출처 규칙
12. **Validator Registry**: deterministic / solver-assisted / semantic 구분
13. **Rollback Matrix**: 결함, 감지 주체, 원인 단계, 무효화 범위, 비용, 사람 개입 조건
14. **Human Review Form**: 승인, 조건부 승인, 반려 기준
15. **Cost-Control Plan**: 정상·실패 경로 호출 수, 후보 수, 캐시, 토큰·비용·시간 중단 조건
16. **Test Plan**: valid / broken / hollow, 단위·통합·회귀·블라인드 풀이·사람 테스트
17. **비교 실험 계획**: A/B/C와 `retry_cap` 2/3 비교
18. **단계별 도입 계획**
    - Phase 0: 사람 제작 퍼즐 구조화
    - Phase 1: AI Shadow Mode
    - Phase 2: 퍼즐 하나 샌드박스 반자동 제작
    - Phase 3: 다중 에셋 퍼즐 반자동 제작
    - Phase 4: Case 단위 제안과 위험 기반 사람 검수
19. **P01 실패 파일럿**: 논리적 불충분성 탐지와 사람 이관
20. **P02 성공 파일럿**: 전체 성공 경로와 binding 국소 롤백
21. **Open Decisions**: 팀이 실제로 결정할 질문, 우선순위, 결정 기한, 결정 주체
22. **가장 자신 없는 부분**: 설계의 약한 고리, 검증 방법, 실패 시 대안

표는 비교에 사용하고, 중요한 판단은 근거를 문장으로 설명합니다. 숫자를 제시할 때 측정값, 가정값, 목표값을 구분합니다.

## 16. 작업 원칙

### 16.1 확정·제안·미정 표시

- 🟢 팀 확정: 계약 또는 확정 문서에 근거
- 🟡 제안: 검토 전 설계 제안
- 🔴 미정: 자료 부족 또는 팀 결정 필요

AI가 제안한 내용을 팀 확정 요구사항처럼 쓰지 않습니다.

### 16.2 사실·추론·제안 구분

- 사실: 근거 파일과 위치 제시
- 추론: 어떤 사실에서 추론했는지 제시
- 제안: 장단점, 비용, 결정 주체 제시

구현·검수하지 않은 것을 완료라고 쓰지 않습니다.

### 16.3 측정되지 않은 수치

성능, 비용, 통과율, 사람 절감 시간은 아직 측정되지 않았다면 `[미측정]`으로 둡니다. 추정이 필요하면 계산식과 가정을 함께 적습니다.

### 16.4 프로젝트에 붙여 설명

일반적인 에이전트 이름만 나열하지 말고 계약 버전, `case-naju-01`, `NAJU-01`, Scene 01~05, P01~P04에 연결합니다. 각 역할의 입력·출력·실패·복구 계약을 제시합니다.

### 16.5 모르는 것을 만들지 않기

나주 설화, 실제 장소, 구현 상태, 에셋, 문서 내용을 추측해 사실처럼 쓰지 않습니다. 합리적 가정이 필요하면 `assumption` 또는 `illustrative_assumption`으로 표시하고 Open Decisions에 연결합니다.

### 16.6 진행과 질문

불확실성이 있어도 안전한 범위에서 가정을 명시하고 설계를 계속합니다. 다만 설계 방향을 완전히 바꾸거나 확정 계약을 변경해야만 진행 가능한 경우에만 시작 전에 질문합니다. 그 외의 결정 사항은 `Open Decisions`에 모읍니다.

### 16.7 최종 판단 기준

좋은 설계는 역할 수가 많은 설계가 아닙니다. 다음을 만족하는 가장 단순한 구조가 좋은 설계입니다.

- 사실과 계약을 어기지 않는다.
- 구현 가능한 퍼즐만 만든다.
- 정보 부족을 창작으로 숨기지 않는다.
- 의미 없는 hollow 퍼즐을 구조 통과만으로 승인하지 않는다.
- 결함을 원인 단계까지 추적한다.
- 통과한 작업을 최대한 보존한다.
- 비용과 재시도를 제한한다.
- 사람이 최종 책임을 질 수 있는 근거를 남긴다.
- 같은 입력과 버전으로 결과를 재현·비교할 수 있다.
