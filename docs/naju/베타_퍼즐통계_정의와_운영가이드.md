## 1. 퍼즐별 이벤트 구조 비교

| | P01 조개 숨구멍 | P03 소리 항아리 | P07 진주 빛 잇기 | P09 물레 고리문 |

핵심 차이:

- **P03 의 incorrect 는 사용자가 틀린 답을 낸 것이 아니다.** 항아리를 하나 놓을 때마다 지금 순서가 판정되므로, 정답으로 가는 이동도 전부 incorrect 로 남는다.
- P01 도 같은 성격이다(삽질마다 판정). 화면 규칙상 조개 구멍을 모두 파야 하므로 **완벽하게 풀어도 incorrect 가 (조개 구멍 수 − 1)번 이상** 생긴다. 게 구멍을 파면 처음부터 다시라서 횟수가 더 늘어난다.
- P09 만 incorrect 가 "의도한 오답 제출"이다.
- P07 은 서버가 과정을 모른다. 행이 있으면 해결한 것이고, 시도 · 오답 · 시간은 알 수 없다.
- P09 는 P07 서버 완료가 선행 조건이다. P07 complete 가 연결 문제로 서버에 닿지 않은 채 남으면 그 세션의 P09 밀기는 409 로 거절되어 **기록이 아예 없다**(Q5 로도 찾을 수 없다).

## 2. 집계 기간 · 대상

### 2.1 파라미터

| 변수 | 기본값 | 뜻 |
|---|---|---|
| `@beta_start_utc` | `2026-11-12 15:00:00` | 베타 시작(KST 11/13 00:00). **실제 시작 시각을 받아 바꾼다** |
| `@beta_end_utc` | `2026-11-13 15:00:00` | 베타 종료(KST 11/14 00:00, 미포함). **실제 종료 시각을 받아 바꾼다** |
| `@asof_utc` | `UTC_TIMESTAMP(6)` | 조회 기준 시각. 이 시각 뒤의 행은 보지 않는다. Q0 출력값을 보고서에 적는다 |
| `@exclude_user_ids` | `'[]'` | 제외할 회원 `app_users.id` JSON 배열(미르님 제공 테스트 회원). 필터에만 쓰고 결과에 내지 않는다 |
| `@exclude_anon_ids` | `'[]'` | 선택: 제외할 팀 게스트 `anonymous_sessions.id` |

KST → UTC: 모든 시각 컬럼은 UTC 를 시간대 없이 담은 `DATETIME(6)` 이다. KST 는 UTC+9 고정(일광절약시간 없음)이므로 **KST 시각 − 9시간** 을 넣는다. 예: KST 11/13 10:00 시작 → `2026-11-13 01:00:00`.

### 2.2 대상 세션(모든 쿼리 공통, `base` CTE)

- `play_sessions.case_id = 'naju-angam-01'` 그리고 `content_version = 1`
  - 나주 FE 는 판 번호를 배포 설정 `VITE_NAJU_NPC_CASE_ID` · `VITE_NAJU_NPC_CONTENT_VERSION` 에서 읽는다. **Q0 의 `sessions_created_in_window:<case>@<version>` 으로 실제 값이 `naju-angam-01@1` 인지 먼저 확인한다.** 다르면 SQL 의 두 값을 고쳐야 한다.
- 소유 회원이 **조회 시점에** `role = 'admin'` 이면 제외.
- `@exclude_user_ids` 의 회원 소유 세션, `@exclude_anon_ids` 의 익명 세션에서 만든 세션 제외.
- 퍼즐 이벤트 = 위 세션의 `interaction_events` 중 §1 의 저장 키에 맞는 행.

### 2.3 세션 생성 시각 기준(코호트) vs 이벤트 발생 시각 기준

| | 코호트(기본 · Q1~Q5) | 이벤트 발생 시각(Q0 참고치) |
|---|---|---|
| 기간 조건 | `play_sessions.created_at` 이 베타 기간 안 | `interaction_events.created_at` 이 베타 기간 안 |
| 베타 전 생성 세션 | **빠진다**(요구사항: 베타 시작 전 생성 세션 제외) | 베타 중 이어서 한 플레이가 들어간다 |
| 기간 끝 뒤 플레이 | 같은 세션이면 `@asof_utc` 까지 들어간다 | 빠진다 |
| 장점 | 세션 하나의 처음과 끝(첫 제출 → 해결)을 온전히 본다 | "그날 일어난 일"의 양 |
| 단점 | 기간 밖 생성 세션의 베타 중 플레이를 놓친다 | 세션이 중간에 잘려 해결률 · 시간이 왜곡된다 |

Q0 의 `event_basis_graded_in_window:<퍼즐>:session_created_before_start` 가 코호트에서 빠진 베타 중 시도량이다. 이 값이 크면 보고서에 적는다.

### 2.4 사람 식별(`principal`)

| 소유 | 식별자 | 비고 |
|---|---|---|
| 회원 세션 | `u:` + `owner_user_id` | |
| 게스트 세션 | `g:` + `owner_anonymous_session_id` | 브라우저 쿠키 하나 = 한 사람으로 본다 |
| 둘 다 없음(레거시) | `l:` + `anonymous_session_id` | `content_version=1` 세션에서는 생기지 않아야 한다(Q5) |

- 접두어로 회원 ID 와 익명 세션 ID 가 같은 값이어도 섞이지 않는다. 식별자는 집계 안에서만 쓰고 결과에 내지 않는다.
- **게스트 → 회원 승계:** 로그인 · 가입하면 그 게스트가 가진 세션의 소유자가 회원으로 바뀌고 `owner_anonymous_session_id` 는 지워진다(`guest_session.py`). 그래서 `owner_type` 은 **조회 시점** 기준이다. 게스트 상태에서 해결하고 나중에 가입한 사람은 Q2 `member_players_solved_while_guest` 로 따로 센다(`guest_session_transfers.transferred_at > 해결 시각`).
- 같은 사람이 다른 기기 · 브라우저 · 쿠키 삭제로 게스트로 오면 다른 사람으로 센다.
- **베타 중 팀원이 게스트로 테스트한 세션은 자동으로 뺄 수 없다.** 팀원이 자기 브라우저의 익명 세션 ID 를 알려 주면 `@exclude_anon_ids` 로 뺄 수 있다. 그 밖에는 보고서에 한계로 적는다.

## 5. SQL 구성

- 파일 하나에 Q0~Q5 독립 문장 6개. **각 문장은 같은 공통 CTE(`prm` … `cohort`)를 처음부터 다시 포함한다.** MySQL 에서 CTE 는 한 문장 안에서만 보이기 때문이다. 공통 CTE 는 한 원본에서 붙여 만들었으므로 여섯 문장의 대상 조건이 글자 그대로 같다.
- 모든 문장은 `SELECT` 다. 앞뒤는 `SET SESSION TRANSACTION READ ONLY` · `MAX_EXECUTION_TIME` · `START TRANSACTION READ ONLY` … `ROLLBACK`.
- 임시 테이블 · 사용자 함수 · 저장 프로시저를 쓰지 않는다(읽기 전용 계정에서 권한 문제 없이 돌게).
- 문자열 비교는 리터럴과 컬럼을 직접 비교한다(리터럴로 만든 CTE 를 조인 키로 쓰면 접속 콜레이션과 테이블 콜레이션이 다를 때 "Illegal mix of collations" 가 날 수 있어 피했다).
- 답안은 `SHA2(payload.answer)` 로 **같은지 비교만** 하고 어떤 결과 컬럼에도 내지 않는다.

## 6. 쿼리별 결과 컬럼과 해석

비공개 표시: 값이 `NULL` 이면 "표본 부족 또는 역산 방지로 비공개"다. 0 은 그대로 보인다.

### 6.1 Q0 — 기준 · 환경 점검(운영 담당자용, `metric`, `value`)

| 컬럼 | 정의 |

### 6.3 Q2 — 퍼즐 × 회원/게스트 플레이어 단위(PM 공유용)

`scope` = `all` · `member` · `guest` · `legacy`. `players`, `players_solved`, `player_solve_rate_pct`(지표 4), `players_solved_in_first_session`, `players_with_retry_session`, `players_with_prior_naju_session`(베타 전 나주 세션이 있던 사람), `players_with_prior_puzzle_attempt`(베타 전에 그 퍼즐을 시도한 사람), `member_players_solved_while_guest`.

비공개 규칙: 칸별 1~4 이면 가림. **같은 퍼즐 안에서 회원/게스트/레거시 중 한 칸이라도 가려지면 그 지표의 나머지 칸도 가린다**(`all` − 보이는 칸 = 가린 칸 역산 방지).

### 6.4 Q3 — 퍼즐별 해결 세션 중앙값 · 백분위(PM 공유용)

`solved_sessions_band`(`lt_5` · `5_9` · `10_19` · `20_plus` — 정확한 건수는 Q1 규칙을 따르도록 구간으로만), `median_sec_first_to_solve` · `p75_…` · `p90_…`, `median_incorrect_solved` · `p90_…`, `median_incorrect_changed_solved` · `p90_…`. 가장 가까운 순위 방식(값 ≥ ⌈p·n⌉ 번째). 중앙값 · p75 는 해결 5건 이상, p90 은 10건 이상일 때만. P07 은 행이 없다.

### 6.5 Q4 — 공통 분모 도달 · 해결 비율(PM 공유용)

`active_sessions_denominator`(코호트 세션 중 나주 상호작용이 1건 이상), `attempted_share_of_active_pct`, `solved_share_of_active_pct`. 네 퍼즐을 나란히 놓을 수 있는 유일한 비율이다. 진행 순서의 영향을 받으므로 "난이도"가 아니라 "도달 · 통과" 로 읽는다.

## 8. 해석 시 주의사항

1. **P03 · P01 의 incorrect 는 "틀린 답을 낸 횟수"가 아니다.** 보고서에는 "정답이 아닌 배치(삽질) 횟수"라고 쓴다.
2. 퍼즐 간 incorrect 와 시간을 나란히 놓고 "어느 퍼즐이 어렵다"고 결론 내리지 않는다. 퍼즐 간 비교는 Q4 와 해결률(P01 · P03 · P09)로 한다.
3. 시간은 "첫 제출부터"다. P09 는 재료를 다 모은 뒤 밀기부터라 짧고, P03 은 낙숫물을 듣는 시간이 첫 배치 전에 빠진다.
4. 미해결에는 진행 중 · 포기 · "처음부터 다시"로 버려진 세션이 섞여 있다. 세션 해결률보다 사람 해결률이 실제에 가깝다.
5. 베타 전에 생성된 세션은 빠진다(Q0 참고치로 크기 확인).
6. 팀원 게스트 테스트는 자동으로 빠지지 않는다.
7. 서버 연결이 안 된 플레이어는 기록이 없다(배포 빌드는 이때 퍼즐을 열지 않는다). P09 는 P07 서버 기록이 없으면 기록이 없다.
8. 조회 기준 시각(`@asof_utc`)과 기준 커밋을 보고서에 반드시 적는다.

## 9. 운영 담당자용 CloudShell 실행 가이드

> 실행은 운영 권한자(미르님 또는 지정자)만, PM 승인 뒤에 한다. 이 문서 작성자는 실행하지 않았다.

### 9.1 사전 조건(PM 확인)

1. **읽기 전용 DB 계정**: 이 네 테이블(`play_sessions`, `interaction_events`, `app_users`, `guest_session_transfers`)에 `SELECT` 만 있는 계정을 권장한다. 마스터 계정 사용은 피한다. 계정 생성은 운영 변경이므로 PM 결정 사항이다.
2. **접속 대상**: 읽기 전용 복제본이 있으면 그쪽. 없으면 주 DB 를 이용자가 적은 시간에.
3. **네트워크**: RDS 가 VPC 안에만 열려 있으면 기본 CloudShell 에서는 닿지 않는다. 같은 VPC 의 CloudShell VPC 환경 등 기존에 승인된 경로를 쓴다. **보안 그룹 · 퍼블릭 접근 설정을 이 작업을 위해 바꾸지 않는다.**
4. 실제 베타 시작 · 종료 시각, 테스트 회원 ID 목록, (있으면) 팀 게스트 익명 세션 ID 목록.

### 9.2 절차

1. 검토를 마친 SQL 파일을 CloudShell 에 올린다(Actions → Upload file). 올린 파일이 검토본과 같은지 확인한다:
   ```bash
   sha256sum 베타_퍼즐통계_P01_P03_P07_P09_읽기전용.sql
   ```
2. 파라미터 칸(`@beta_start_utc` · `@beta_end_utc` · `@exclude_user_ids` · `@exclude_anon_ids`)만 편집기로 고친다. 다른 줄은 고치지 않는다.
   ```bash
   nano 베타_퍼즐통계_P01_P03_P07_P09_읽기전용.sql
   ```
3. MySQL 호환 클라이언트를 조직 표준 방식으로 준비하고, 접속 정보는 환경 변수로만 둔다(비밀번호는 `-p` 프롬프트로 입력 — 명령줄 · 파일 · 채팅에 남기지 않는다).
   ```bash
   export DB_HOST='<읽기 복제본 또는 RDS 엔드포인트>'
   export DB_NAME='<DB 이름>'
   export DB_RO_USER='<읽기 전용 계정>'
   ```
4. 접속과 권한만 먼저 확인한다:
   ```bash
   mysql --host="$DB_HOST" --user="$DB_RO_USER" -p --database="$DB_NAME" \
         -e "SELECT VERSION(), CURRENT_USER(), @@transaction_read_only; SHOW GRANTS;"
   ```
   MySQL 8 인지, 권한이 `SELECT` 뿐인지 본다. TLS 옵션은 클라이언트에 따라 `--ssl-mode=REQUIRED`(MySQL) 또는 `--ssl`(MariaDB) 이다.
5. 한 접속에서 파일 전체를 실행하고 결과를 파일로 받는다:
   ```bash
   mysql --host="$DB_HOST" --user="$DB_RO_USER" -p --database="$DB_NAME" --table \
         < 베타_퍼즐통계_P01_P03_P07_P09_읽기전용.sql > 결과_$(date -u +%Y%m%dT%H%MZ).txt
   ```
   GUI 도구처럼 문장마다 접속을 새로 여는 도구는 `@변수` 가 사라지므로 쓰지 않는다.
6. 결과 파일에서 **Q0 · Q5 를 먼저 본다**(§6.1 · §6.6). 이상이 있으면 PM 공유를 멈추고 BE 와 원인을 본다.
7. Q1~Q4 만 §10 양식으로 옮긴다. 결과 파일을 내려받은 뒤 CloudShell 에서 지운다(`rm 결과_*.txt`). CloudShell 홈 디렉터리는 세션이 끝나도 남는다.

### 9.3 운영에서 절대 하지 말 것

- `INSERT` · `UPDATE` · `DELETE` · `REPLACE` · `TRUNCATE` · `ALTER` · `CREATE` · `DROP` · `GRANT` · `SET GLOBAL` · `KILL` · `LOCK TABLES` · `SELECT … FOR UPDATE` · `INTO OUTFILE` 를 이 파일에 덧붙이거나 따로 실행하지 않는다.
- `payload_json` · `response_json` · `state_json` · `email` · ID 컬럼을 `SELECT` 해서 화면이나 파일로 꺼내지 않는다(정답 · 개인정보 노출).
- 행 단위 결과 · `mysqldump` · 테이블 내보내기를 만들지 않는다.
- `READ ONLY` 트랜잭션 · `MAX_EXECUTION_TIME` 줄을 지우지 않는다. 느리면 끊고 시간대를 바꾼다(`MAX_EXECUTION_TIME` 을 늘리거나 반복 실행하지 않는다).
- 이 작업을 위해 보안 그룹 · DB 파라미터 · 계정 권한을 바꾸지 않는다(필요하면 PM 승인 후 별도 작업).
- 서비스 재시작 · `alembic` · 배포 명령을 실행하지 않는다.
- 비밀번호 · 엔드포인트 · 결과 원문을 채팅에 붙이지 않는다.

### 9.4 부하

- `interaction_events` 는 `play_session_id` 인덱스로 대상 세션의 행만 읽는다.
- `play_sessions` 는 `case_id` · `created_at` 인덱스가 없어 전체를 훑는다(베타 규모에서는 작다). `prior_sess` 도 같다.
- 여섯 문장이 같은 CTE 를 매번 다시 계산한다. 문장당 60초 상한, 복제본 또는 한가한 시간에 실행.

## 11. 격리 DB 검증 절차(추후 — 이번에는 만들지 않았다)

실행 전 조건:

- **새로 만든 빈 MySQL 8 인스턴스**만 쓴다. 기존 `MySQL80` 서비스(개발용 DB) · 운영 · 공유 DB 는 쓰지 않는다.
- 저장소 관례를 따른다: 데이터 디렉터리를 작업용 임시 폴더에 새로 만들고, 기존과 겹치지 않는 포트, `127.0.0.1` 바인드, DB 이름은 `test_` 로 시작. 테스트의 격리 확인 방식(`*_MYSQL_ISOLATED=1`, DB 이름 접두어, 데이터 디렉터리 경로 대조)과 같은 점검을 먼저 한다.
- 접속 대상이 그 인스턴스인지 `SELECT @@port, @@datadir, DATABASE()` 로 확인한 뒤에만 진행한다.

절차:

1. 임시 데이터 디렉터리로 `mysqld --initialize-insecure` → 별도 포트로 기동.
2. `test_puzzle_stats_<임의>` DB 생성, 백엔드 `alembic upgrade head` 로 실제 스키마를 만든다(그 DB 를 가리키는 환경 변수로만).
3. 합성 데이터 넣기(실제 이용자 · 정답 없이, 답안은 임의 문자열). 최소 시나리오:
   - 게스트 세션: P03 incorrect 3(그중 같은 답 1) → correct, 이어서 already_completed 1
   - 회원 세션: P01 incorrect 2 → correct, P07 complete correct, P09 incorrect 1 → correct
   - 게스트로 P03 해결 후 `guest_session_transfers` 로 회원 승계된 세션
   - 같은 게스트의 "처음부터 다시" 두 번째 세션(미해결)
   - 베타 시작 전 생성 세션(베타 중 시도 포함) · 베타 종료 뒤 시도
   - 관리자 소유 세션 · 제외 목록 회원 세션 · `content_version` NULL 세션
   - `state_json.attempt_counts` 를 이벤트 수와 일부러 다르게 한 세션 1개
   - 표본 1~4 칸이 생기는 경우와 5 이상인 경우
4. SQL 파일을 그 인스턴스에서 실행하고, 시나리오별 기대값(손으로 계산)과 Q0~Q5 출력을 대조한다. 특히: 제외 조건, 코호트/이벤트 기준 차이, `nth_session_in_window`, `already_completed` 제외, `repeat_same_answer`, 비공개 · 2차 비공개, P07 표시.
5. `EXPLAIN` 으로 `interaction_events` 가 `ix_interaction_events_play_session_id` 를 쓰는지 본다.
6. 인스턴스를 멈추고 임시 데이터 디렉터리를 지운다.

## 12. 정적 검토 기록

이전 P03 초안(대화로 전달된 것) 대비 고친 점:

| 이전 문제 | 수정 |
|---|---|
| Q0 만 `content_version` · 관리자 제외 · `interaction_type` 조건이 없음 | 공통 `base` CTE 를 모든 문장에 같은 글자로 포함 |
| Q2~Q4 가 "WITH 절 뒤에 붙이라"는 주석 조각 | 6개 문장 모두 공통 CTE 를 포함한 독립 문장 |
| `first_client_at = MIN(client_timestamp)` 라 기기 시계 역행 검사가 걸릴 수 없음 | 첫 정상 시도(`seq = 1`)의 `client_timestamp` |
| `TIMESTAMPDIFF(SECOND)` 로 초 이하 버림 | 마이크로초 차이 ÷ 10⁶, 소수 첫째 자리 |
| 사람 식별자에 회원 · 게스트 · 레거시 구분 없음 | `u:` · `g:` · `l:` 접두어 |
| `first_session` 이 평생 첫 세션처럼 보임 | `nth_session_in_window`(기간 내 순번) + 베타 전 이력 칸 |
| 해결 뒤 제출이 오답 · 시도에 섞일 수 있음 | 정상 시도 = incorrect · correct 만 |
| 비공개가 구간 분포에만 있음 | 모든 공유용 칸에 5 미만 · 여집합 · 나눔 칸 2차 비공개 |
| P03 전용 | P01 · P03 · P07 · P09 공통, P07 의 `complete` + Object ID 저장 반영 |
| 리터럴 CTE 조인 키(콜레이션 충돌 가능) | 리터럴 직접 비교 |
| 집계 함수 안 서브쿼리(`SUM(EXISTS …)`) | 행 단위 플래그 뒤 집계 |
| (11/11 추가) Q5 의 `incorrect_after_correct` · `already_completed_events` · `sessions_only_already_completed` 가 0 건이면 행이 사라져 "0 이어야 함"을 확인할 수 없음 | 퍼즐별 집계(`per_puzzle`)에 LEFT JOIN 해서 0 도 한 행으로 낸다 + 합계 행 추가 |

검증 자료: 합성 데이터 · 예상값 · 실행 순서는 [`베타_퍼즐통계_검증/검증_절차와_예상값.md`](./베타_퍼즐통계_검증/검증_절차와_예상값.md).

기계적 점검(파이썬 정규식, DB 접속 없음): 문장 15개(설정 7 · 쿼리 6 · 시작/종료 2), 쓰기 · DDL · `SET GLOBAL` 키워드 없음, 문장별 괄호 · 따옴표 균형, 모든 `FROM`/`JOIN` 대상이 정의된 CTE 또는 실제 테이블 4개, 별칭 붙은 컬럼이 실제 모델 컬럼, 최종 결과 컬럼에 ID · 이메일 · payload · 해시 없음. **MySQL 파서 · 실행 검증은 하지 않았다.**
