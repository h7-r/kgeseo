## 2. 합성 데이터 안전 조건

- ID: 고정 패턴 UUID(`aaaaaaaa-…` 사용자, `bbbbbbbb-…` 익명 세션, `cccccccc-…` 플레이 세션, `dddddddd-…`/`eeeeeeee-…` 이벤트). 실제 ID 아님.
- 이메일 `syn-user-NN@example.invalid`, 닉네임 `synNN`. 실제 사용자 정보 없음.
- 답안: `syn-p03-o1` · `syn-p01-ab` 같은 임의 문자열. **실제 퍼즐 정답이 아니다.** 정답 여부는 `result_type` 에 직접 적어 넣었다(서버 판정을 거치지 않는 데이터).
- `content_fingerprint` 는 `sha256:000…`(가짜), 토큰 해시는 합성 문자열의 SHA-256.
- 운영용 SQL 에는 아무것도 덧붙이지 않았다. 테스트값은 실행본(`make_test_queries.py` 출력)에만 들어간다.

| 실행 계획 · 부하 | `EXPLAIN` 에서 `interaction_events` 접근이 `ix_interaction_events_play_session_id` 또는 `uq_interaction_events_play_session_client_event` 를 쓴다. `play_sessions` 전체 훑기는 예상된 동작(인덱스 없음). 각 문장이 `MAX_EXECUTION_TIME`(60초) 안에 끝난다 |
| 콜레이션 | 오류 `Illegal mix of collations` 가 없다. 운영 테이블 콜레이션을 알면 같은 값으로 서버를 띄워 한 번 더 돌린다 |

불일치가 나면: 먼저 예상값의 근거(§3 시나리오 · `make_fixture.py`)를 다시 확인하고, SQL 이 틀렸다고 판단되면 운영 SQL 을 고친 뒤 `make_test_queries.py` → 실행 → 비교를 처음부터 다시 한다. 예상값을 결과에 맞춰 고치지 않는다.

## 6. 독립 MySQL 8 환경에서 실행하는 순서(추후)

> 이번 단계에서는 실행하지 않았다. Docker 설치 · 기존 MySQL80 사용 금지 조건은 그대로다. 아래는 **Docker 가 따로 준비된 뒤**의 절차다.

### 6.1 환경 만들기

1. 저장소 밖 임시 작업 폴더를 정한다(예: `%TEMP%\kgeseo-stats-verify`). 비밀번호는 실행할 때마다 새로 만든 임의 값을 쓰고 어디에도 저장하지 않는다.
2. 독립 컨테이너(프로젝트 · 기존 MySQL80 과 무관, 127.0.0.1 에만, **서버 포트도 3306 이 아니게**):
   ```bash
   docker run -d --name kgeseo-stats-verify \
     -e MYSQL_ROOT_PASSWORD="$ROOT_PW" \
     -e MYSQL_DATABASE=test_puzzle_stats_1111 \
     -e MYSQL_USER=stats_verify -e MYSQL_PASSWORD="$APP_PW" \
     -p 127.0.0.1:3407:3407 \
     mysql:8.0 --port=3407 --character-set-server=utf8mb4
   ```
   - `--port=3407` 이 없으면 컨테이너 안 `@@port` 가 3306 이라 fixture 가드 2 에 걸린다(의도된 보호).
   - 운영 RDS 의 MySQL 부 버전 · 콜레이션을 알면 이미지 태그와 `--collation-server` 를 같게 맞춘다.
3. 확인(이 값이 아니면 멈춘다):
   ```bash
   mysql -h 127.0.0.1 -P 3407 -u stats_verify -p test_puzzle_stats_1111 \
     -e "SELECT VERSION(), @@port, @@hostname, DATABASE(), @@character_set_server, @@collation_server;"
   ```

### 6.2 스키마 만들기(실제 alembic 마이그레이션)

1. **`.env` 가 없는** 새 worktree 를 저장소 밖 임시 폴더에 만든다(기존 worktree 를 쓰지 않는다 — 기존 `backend/.env` 가 개발 DB 를 가리킬 수 있다):
   ```bash
   git -C <저장소> worktree add --detach "$TMP/kgeseo-verify-wt" <검증할 커밋>
   ```
2. 그 worktree 의 `backend` 에서 가상환경을 만들고 `requirements.txt` 를 설치한다.
3. 접속 대상을 **환경 변수로만** 준다:
   `DB_HOST=127.0.0.1 DB_PORT=3407 DB_USER=stats_verify DB_PASSWORD=$APP_PW DB_NAME=test_puzzle_stats_1111`
4. 대상 확인(비밀번호는 출력하지 않는다):
   ```bash
   python -c "from app.core.config import settings as s; print(s.db_host, s.db_port, s.db_name)"
   ```
   `127.0.0.1 3407 test_puzzle_stats_1111` 이 아니면 멈춘다.
5. `alembic upgrade head` → `alembic current` 로 head 확인.

### 6.3 데이터 넣기 · 실행 · 비교

```bash
V=<이 폴더>        # docs/naju/베타_퍼즐통계_검증
R="$TMP/kgeseo-stats-verify/run"
M="mysql -h 127.0.0.1 -P 3407 -u stats_verify -p$APP_PW test_puzzle_stats_1111 --default-character-set=utf8mb4"

# 1) 합성 데이터(가드가 하나라도 걸리면 여기서 멈춘다 — --force 를 쓰지 않는다)
$M < "$V/fixture_테스트전용_합성데이터.sql"

# 2) 테스트 실행본 만들기(운영 SQL 은 그대로)
python -I "$V/make_test_queries.py" "$R/queries"

# 3) 쿼리별 실행 — 결과 집합 하나씩 TSV 로
for i in 0 1 2 3 4 5; do $M --batch < "$R/queries/q$i.sql" > "$R/q$i.tsv"; done

# 4) 비교
python -I "$V/compare_results.py" "$R"

# 5) 실행 계획(같은 파라미터로, 각 쿼리 본문 앞에 EXPLAIN FORMAT=TREE 를 붙여 따로 확인)
```

명령줄 `-p$APP_PW` 대신 `--login-path` 나 프롬프트를 써도 된다. 비밀번호를 파일 · 기록 · 채팅에 남기지 않는다.

### 6.4 정리

```bash
docker rm -f kgeseo-stats-verify          # 컨테이너와 그 안의 데이터 삭제
git -C <저장소> worktree remove "$TMP/kgeseo-verify-wt"
rm -rf "$TMP/kgeseo-stats-verify"          # 실행본 · 결과
```

결과 TSV 는 합성 데이터라 개인정보는 없지만, 검증 보고에는 `compare_results.py` 출력과 `VERSION()` · 커밋만 옮긴다.

## 7. 아직 확인되지 않은 것

- 실제 MySQL 8 에서의 문법 · 실행(가장 큰 미확인 항목). 특히 `CAST(… AS JSON)` 세션 변수, `JSON_CONTAINS`, `WINDOW` 절, 별칭 `GROUP BY`, `DO (스칼라 서브쿼리)` 가드의 동작.
- 운영 테이블 콜레이션과의 호환(리터럴 비교 · `CONCAT` 결과 조인).
- `alembic upgrade head` 로 만든 실제 스키마의 NOT NULL · FK 가 fixture INSERT 와 맞는지(모델 기준으로 맞췄다).
- 실행 계획과 실행 시간(합성 데이터는 작아서 운영 부하를 대표하지 않는다).
- MySQL 이 숫자를 내는 모양(`2.6` · `2.6000` 등)은 비교기가 값으로 비교하므로 통과하지만, 실제 출력 형식은 확인 전이다.
