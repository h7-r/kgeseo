> 기준: 「왜곡 로비 멀티플레이 설계 v0.19」 6절 0단계, 7.1절 「기기 성능」, 7.4절 기록 규칙
> 측정 기기: LG 15UG50P(Iris Xe · 8GB) — 측정은 미르가 한다
> 이 결과는 **예비 측정**이다. 가짜 아바타 결과로 공개 판정을 하지 않는다(7.1 「기기 성능」은 실제 연결로 다시 잰다).
> 이 문서와 장치가 갖춰졌다는 것은 「측정 준비 완료」다. 설계 6절 0단계의 완료 기준(기기 기준 만족)은 실측 전이다 [미측정].

## 1. 무엇을 재나

로비 서버 없이, 본부실에 **나 1명**일 때와 **나 + 가짜 아바타 9명**(방 정원 10)일 때의 프레임을 같은 조건으로 비교한다.

- 동선: **나는 정해진 자리에 서 있고**, 가짜 아바타 9명이 본부실 안 고리 세 개를 걷기 속도로 계속 돈다(모두 걷기 = 가장 무거운 경우). 실제 참가자가 함께 움직이는 시험(7.1 「첫 만남과 본편」 등)과는 다르다.

| 지표 | 뜻 |
|---|---|
| 평균 FPS | 측정한 프레임 수 ÷ 실제로 걸린 시간 |
| p95 프레임 | 프레임 간격(보정하지 않은 값)을 짧은 순서로 늘어놓았을 때 95번째 백분위 |
| 가장 긴 프레임 · 50ms 넘은 프레임 수 | 눈에 띄는 멈칫 |
| 등장 때 가장 긴 프레임 | 가짜 아바타 9명이 **한꺼번에** 나타나는 동안의 가장 긴 프레임. 실제로는 한 명씩 들어오므로 최악값이다 |

시작 목표(7.1, 🟡): 나 + 9명에서 **평균 30fps 이상**이고, 브라우저 멈춤·그래픽 오류·출동 실패가 없어야 한다. 이 장치는 출동을 시험하지 않는다 — 출동은 따로 확인하고, 안 했으면 `[미확인]`으로 둔다.

- 가짜 아바타는 실제 내 캐릭터와 같은 컴포넌트(`LobbyChibi`, 같은 몸체·툰·외곽선 설정)다. 아바타 하나에 상자 하나를 두고 매 프레임 값만 바꾼다. 모델은 처음 한 번만 만든다.
- 원격 캐릭터라서 충돌·퍼즐 상호작용에는 들어가지 않는다. 동선이 책상을 지나가도 된다.
- 평소 `npm run dev`(5173)와 `vite build`(`dist/`)에는 들어가지 않는다.
- 「등장 완료」는 모델이 붙은(마운트) 시점이다. 셰이더 준비까지 따로 확인하지 않으므로 그 뒤 5초를 예열로 버린다.

## 3. 준비 (맥에서 한 번)

판정용 숫자는 **배포와 같은 빌드**로 잰다. 개발 서버(React 개발판)는 장치 점검용이다.

```bash
# 저장소 루트에서. 추적 파일을 고치지 않은 커밋에서 빌드한다(고친 채면 결과 줄 커밋에 +수정이 붙고, 판정 기록에 쓰지 않는다)
npx vite build --config vite.lobby-perf.config.ts
npx vite preview --config vite.lobby-perf.config.ts --host   # --host: 같은 망의 노트북에서 접속
ipconfig getifaddr en0                                       # 맥의 와이파이 IP
```

- 빌드는 `public/`을 통째로 복사해 **약 3.3GB**다(11/6 기준). 측정이 끝나면 지운다(6절).
- 커밋 칸은 빌드할 때 찍힌다. 개발 서버는 **켤 때** 한 번 찍으므로, 켠 뒤에 파일을 고쳐도 `+수정`이 붙지 않는다 — 판정 기록은 빌드로만 잰다.
- 노트북은 브라우저만 쓴다. 저장소를 받을 필요가 없다. 주소는 `http://<맥 IP>:5181`.

### 노트북에서 맥에 접속할 때의 함정

- **접속이 안 되면**: 맥 「시스템 설정 → 네트워크 → 방화벽」에서 `node`의 들어오는 연결을 허용한다. 같은 와이파이여도 기기끼리 막는 망(학교·공용 와이파이)에서는 안 된다 — 휴대폰 핫스팟 등 다른 망을 쓴다.
- **주소는 빌드 때 정해진다**(`shared/env.ts`). 빌드할 때 `VITE_API_ORIGIN`·`VITE_ASSET_BASE`에 `localhost`가 들어 있으면 노트북 자신을 가리켜 에셋을 못 받는다. 기본값(비어 있음)이면 같은 출처라 맥에서 받는다.
- `/api`는 미리보기 서버가 **맥의** `127.0.0.1:8000`으로 넘긴다. 백엔드가 꺼져 있어도 FPS 측정에는 상관없다.
- `http://IP`는 보안 출처가 아니다. 클립보드 복사가 막히면 패널이 글상자로 보여 준다. 나주 팩 복호화(`crypto.subtle`)·자물쇠 제출(`crypto.randomUUID`)도 막힐 수 있으니 **이 방식으로 출동·나주 진입을 시험하지 않는다.**

## 4. 고정할 조건

두 조건(1명·10명)을 **같은 노트북·같은 브라우저·같은 창 크기·같은 그래픽 설정**으로 번갈아 잰다.

- [ ] 노트북 전원 연결, 다른 프로그램·탭 닫기
- [ ] Chrome **시크릿 창**(확장 프로그램 꺼짐). 측정마다 **열려 있는 시크릿 창을 모두 닫은 뒤** 새로 연다 — 그래야 저장값(게임 설정·내 외형·위치)이 기본값으로 돌아간다
- [ ] 창 최대화 후 크기 그대로 유지. 측정 중 **창 크기를 바꾸거나 탭을 숨기면 그 회차는 버리고 다시 잰다**
- [ ] 게임 설정을 바꾸지 않는다(해상도 「자동」 그대로). 결과의 `화면 · dpr`이 두 조건에서 같은지 본다
- [ ] 측정 사이 1분 쉬기(열), 순서는 **0 → 9 → 0 → 9**처럼 번갈아 두 번 이상

## 5. 절차

1. 시크릿 창에서 아래 주소 중 하나를 연다.
   - 나 1명: `http://<맥 IP>:5181/?bots=0&input=always`
   - 나 + 9명: `http://<맥 IP>:5181/?bots=9&input=always`
2. 게임이 복도 화면까지 뜨면 왼쪽 위 패널의 **[측정 시작]**을 누른다.
3. 손을 뗀다. 장치가 알아서 진행한다(약 70초).
   - 본부실 (−14, 7)로 순간이동하고 시선을 방 한가운데로 고정 → 3초 자리 잡기
   - 가짜 아바타 등장(9명일 때) → 5초 예열 → **60초 측정**
4. 「끝」이 뜨면 **[결과 복사]** → 7절 기록표에 붙이고 `[기기]`·`[멈춤·화면 오류]`·`[통과]`·`[확인자]`를 채운다. 출동 칸은 따로 시험하지 않았으면 `[미확인]` 그대로 둔다.
   - 복사가 막히면 패널 아래 글상자의 줄을 선택해 옮긴다.
5. 다음 측정은 시크릿 창을 **모두 닫고** 새로 연다. 새로고침만 하면 브라우저 캐시와 장치 상태가 남아 등장 값이 달라질 수 있다.

`?input=always`는 포인터 잠금 없이 3인칭 카메라를 정상으로 돌리기 위한 것이다. 두 조건 모두 같게 붙인다.

### 주소 옵션 (원인 가르기용 — 판정 기록과 구분해서 적는다)

| 옵션 | 뜻 |
|---|---|
| `bots=0~9` | 가짜 아바타 수(기본 9) |
| `botMotion=idle` | 가짜 아바타가 제자리에 서 있다(기본은 모두 걷기) |
| `outline=off` · `toon=off` · `fx=off` | 기존 화면 옵션(외곽선·툰·후처리 끄기). 나와 가짜 아바타 모두에 적용된다 |
| `perfSeconds=10` | 장치 점검용으로 측정을 짧게. **판정 기록은 기본 60초** |

결과 줄의 「환경」 칸에 빌드/개발과 주소 옵션이 자동으로 들어간다.

## 8. 참고 — 장치 점검 때 맥에서 본 값 (판정에 쓰지 않음)

2026-11-06, Apple M5 Max · Chrome 156 · 2592×1359 · dpr 1.5 · 화면 120Hz, **10초 점검**(`perfSeconds=10`). 장치가 도는지 보려고 잰 값이라 위 기록표에 넣지 않는다.

| 조건 | 빌드 | 평균 FPS | p95(ms) | 등장 최대(ms) |
|---|---|---|---|---|
| 나 + 0 | 개발 서버 | 120.0 | 8.7 | — |
| 나 + 9 서 있음 | 개발 서버 | 119.9 | 8.5 | 456.2 |
| 나 + 9 걷기 | 개발 서버 | 22.2 | 45.8 | 432.1 |
| 나 + 9 걷기, 외곽선·툰 끔 | 개발 서버 | 22.7 | 44.6 | 399.4 |
| 나 + 0 | 빌드 미리보기 | 120.1 | 8.5 | — |
| 나 + 9 걷기 | 빌드 미리보기 | 22.5 | 45.3 | 382.5 |

- 이번 측정에서 **서 있는 9명은 FPS가 거의 떨어지지 않았고, 걷는 9명은 약 1/5로 떨어졌다.** 외곽선·툰을 꺼도 그대로였다. 그림자 축소는 아직 재지 않았다.
- **CPU 프로파일**(걷는 9명, 개발 서버, 6초, `node tools/lobby-perf-profile.mjs <저장 경로>`로 다시 뜰 수 있다): 자기 시간 상위는 three.js `multiplyMatrices` 31% · `updateWorldMatrix` 21% · `applyBoneTransform` 15%. three.js 안에서 쓴 시간을 부른 쪽 첫 함수로 넘겨 센 **표본 비중의 81.8%가 `naju01/src/avatar/footContactIk.ts`의 `lowestSoleY` 안**이다(11/6 두 번 떠서 82.1% · 81.8%). CPU 사용률이 아니라 프로파일 표본 비중이다.
- 그 경로: 걷기·달리기처럼 제자리 클립이 아니면 `ChibiGameAvatar.tsx` 333~337줄이 매 프레임 밑창 정점 전부에 `lowestSoleY`를 돌린다(서 있을 때는 324~331줄 캐시). `lowestSoleY`(61~79줄)는 정점마다 `getVertexPosition`(CPU 스키닝, 뼈 행렬 최대 4개 곱)과 `localToWorld`(부모까지 올라가며 행렬 갱신)를 부른다. 같은 파일의 접지 IK(170줄)도 `lowestSoleY`를 부르지만, Tripo 동작은 접지 IK가 꺼져 있어(`motionCorrection.ts` `TRIPO_CORRECTION.footContactEnabled: false`) 이번 경로에는 없다.
- **실험(코드 수정 아님)**: 측정 페이지 안에서만 스킨 메시의 `localToWorld`가 정점마다 부모 행렬을 다시 계산하지 않게(이미 계산된 `matrixWorld`만 곱하게) 바꿔 번갈아 쟀다. 걷는 9명, 개발 서버, 10초씩: **23.5 · 24.5fps → 48.3 · 47.6fps**(p95 43.4 · 41.4ms → 21.1 · 21.5ms). `ChibiGameAvatar.tsx` 310줄이 바로 앞에서 `group.updateMatrixWorld(true)`를 하므로 결과는 같아야 한다고 코드로 판단했다(화면 비교는 안 함). 남은 비용은 정점마다의 CPU 스키닝이다.
- 그래서 이번 결과로는, 설계 6절의 「부족하면 외곽선·그림자부터 줄인다」보다 **걷는 원격 캐릭터의 발바닥 계산을 줄이는 것이 먼저**로 보인다.

### 8.1 고친 뒤 (2026-11-06, 미르 허락으로 `naju01/src/avatar/footContactIk.ts` 수정)

- `lowestSoleY`가 정점마다 하던 부모 행렬 갱신을 **밑창 메시마다 한 번**으로 줄였다(위 실험과 같은 내용을 코드로).
- 같은 값인지: 실제 스킨 메시 110개 · 정점 8,963개에서 옛 계산과 새 계산의 높이 차 최대 **2.2×10⁻¹⁶**(부동소수점 오차).
- 맥 10초 점검(개발 서버): 걷는 9명 **48.2 · 48.5fps**(p95 21.2 · 21.1ms), 나 혼자 120.0fps. 고치기 전 22~24fps.
- 남은 비용은 정점마다의 CPU 스키닝(`getVertexPosition`)이다. LG에서 30fps가 안 되면 걷는 동안의 밑창 높이를 줄여 구하는 다음 단계를 검토한다.
- LG 기준값: 고치기 전 커밋(이 문서를 처음 넣은 0단계 커밋)과 고친 뒤 커밋을 같은 절차로 각각 빌드해 잰다.
