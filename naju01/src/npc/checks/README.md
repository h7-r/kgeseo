# NPC 회귀 검사

나주 동행 NPC(`naju01/src/npc/`)의 회귀 검사 두 개. 둘 다 **개발 서버에 떠 있는 실제 나주 맵**을 헤드리스 크롬으로 열어 검사한다.
따로 저장해 둔 데이터나 자체 로더가 없다 — 지형(블렌더 높이표 포함)과 소품 충돌은 그 자리의 씬에서 읽고,
TS 모듈은 개발 서버가 변환한다(`naju01/tools/check-baked-terrain.mjs` 와 같은 방식).

## 실행

```powershell
npx.cmd vite naju01                                         # 다른 창 · http://localhost:5174
node naju01/src/npc/checks/run-npc-checks.mjs               # 기본 주소 http://localhost:5174/
node naju01/src/npc/checks/run-npc-checks.mjs http://localhost:5184/ --json out.json   # 다른 포트 · 측정값 저장
node naju01/src/npc/checks/browser-follow.mjs               # 통합 패치가 들어간 서버에서
```

- 저장소 뿌리에서 돌린다(`playwright` 는 뿌리 `node_modules` 의 개발 의존성). 새 패키지는 필요 없다.
- 헤드리스 Chrome 은 포인터 잠금 직후 첫 키를 버리고, 잠금이 늦게 붙기도 한다. 시작할 때 잠금을 기다린 뒤 Shift 가 실제로 닿을 때까지 채운다(10/21 — 전에는 300 ms 고정 대기라 가끔 W 가 먹혀 「?npc 없음」 이동 0 m 로 실패했다).
- 브라우저: 시스템 Chrome 을 먼저 쓰고, 없으면 Playwright 기본 Chromium 을 쓴다(그때는 `npx playwright install chromium` 이 한 번 필요하다 — 이 저장소의 `naju01/tools/headlessPage.mjs` 도 같은 Chromium 을 쓴다).
- 씬이 다 붙을 때까지(소품 수·지면 높이 표본이 6 초 동안 그대로) 기다린 뒤 검사한다. 한 번에 1–3 분.
- 끝에 `결과: 통과/전체` 를 찍고, 실패나 페이지 오류가 있으면 종료 코드 1.

## 검사가 씬에 하는 일

- 치운 차단물(`terrain.clearedBlockers`)을 잠깐 바꿨다가 **검사 전 상태로 되돌린다.**
- 계측 스위치(`npcProfile.enabled`)를 켰다가 원래대로 둔다.
- 플레이어·카메라·씬 진행은 건드리지 않는다. 시나리오의 플레이어는 따로 만든 상자(AvatarLink 모양)다.
- 게임 이벤트 묶음(I)은 게임 상태(`stage` · `focus`)를 읽기만 하고, 읽기 전·후가 같은지 검사한다. 나머지는 꾸민 스냅숏으로 돈다.
- `browser-follow.mjs` 의 [2c] 는 실제 게임 상태를 바꾼다(`endScene(2)` · 순간 이동) — 절마다 새 페이지라 다른 절에 남지 않는다.
- [2d] 대화: 1인칭은 NPC 를 Idle 로 세우고 그 1.5 m 옆으로 옮겨 NPC 를 보게 한 뒤(순간이동 방향은 ±X·±Z 만) F·Enter·Esc·거리 종료·KeyE 를 본다.
  3인칭은 Follow 그대로(카메라가 뒤라 NPC 가 화면 안) 대화 중 걷기 · 끝낸 뒤 재합류를 본다.
- [2e] 도움 제안: 실제 기준(정체 300 s)으로는 몇 분을 기다려야 해서 개발 훅 `help.configure` 로 그 페이지에서만 임계값 · 쿨다운 · 유효 시간을 줄인다.
  게임 · 검사 기준값은 그대로이고, 이 절은 「판단 → 제안 → F 수락 · G 거절 · 숨김 · 진행 만료」 연결만 본다.
- [2f] AI 대사 공급자: 개발 훅 `dialog.useMockAi` 로 가짜 전송(ok · invalid · error · slow)을 끼워 실제 게임 루프에서 검증 · fallback · 시간 초과를 본다. 실제 모델 · 백엔드는 없다.
- [2g] HTTP AI 전송: Playwright `page.route` 가 `/api/v1/npc/dialogue` 를 네트워크에서 가로채 모의 응답(200 · 503 · 끊김 · 잘못된 JSON · 다른 차례 · 3.5 s 지연)을 준다. 가로채지 않으면 개발 서버가 받아 fallback 으로 떨어지는 것도 본다.
- [2f] · [2g] 는 전송 층을 보려고 `{ contentPolicy: "off" }` 로 연다(자유 문장이 화면에 나온다 — 게임 경로 아님). [2h] 가 게임 기본(정책 켬)을 본다.
- J 묶음의 「시선 판정 차이」는 렌더 무리를 인스턴스마다 임시 메시로 세워 광선을 쏜다 — 무리는 구역 초점이 그리는 개수를 바꿔 묶음 구가 낡기 때문이다.
  카메라 둘레 12 m(그리는 곳)의 소품만 고른다.

## 알아 둘 것

- 시나리오 플레이어 경로는 실제 플레이어 충돌(`propColliders.blockedAt` · `terrain.blockedAt` · 물·벼랑)로 걸을 수 있는지 먼저 검사한다. 「우회 부하」만 예외(일부러 소품을 끼고 돌아 비용을 잰다).
- 걸음 비용 기준(4 ms 초과 ≤ 1%, 16.7 ms 초과 0)은 헤드리스 값이다. 헤드리스는 실제 GPU 브라우저보다 느리고 흔들린다.
- 소품 판정의 「물리 기준」은 NPC 가 실제로 뜨는 높이 규칙(`terrain.ts` 의 `groundHeight`)을 0.05 m 로 짚은 것이고, 이것보다 덜 막으면 실패다. 「보수 기준」(생 지면)과의 차이는 참고로만 찍는다.
- 계측(`../npcProfiler.ts`)은 개발 서버에서 `?npc&npcprof` 로 열거나 콘솔에서 `__game.npcFollow.profile.enable()` 로 켠다. 결과는 `__game.npcFollow.profile.report` (느린 프레임 상위 10, 단계별 시간, 경로·후보·지형 표본 횟수).
